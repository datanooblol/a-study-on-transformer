Applied Project: Next-Purchase Forecasting

A decoder-only (GPT-style) model that reads a customer's purchase history and predicts three things about their next purchase at once: which policy, at what age, for what price.

Files to open alongside this lesson
  • package/insurance_decoder_block.py — EventEmbedding, InsuranceDecoderBlock
  • train_insurance.py — mock data, UncertaintyWeightedLoss, training loop, predict()

Step 1 — fuse three different feature types into one event vector

Each purchase event has a categorical feature (policy) and two continuous features (age, price). They can't share one embedding table, so each gets its own projection to d_model, and the three are simply summed into one vector per event.

package/insurance_decoder_block.py — EventEmbedding
self.policy_emb = nn.Embedding(num_embeddings=num_policies, embedding_dim=d_model)
self.age_proj   = nn.Linear(1, d_model)
self.price_proj = nn.Linear(1, d_model)

def forward(self, policy, age, price):
    return self.policy_emb(policy) + self.age_proj(age) + self.price_proj(price)

💡 Tip

Sum instead of concatenate keeps the vector at d_model regardless of how many feature types you fuse — each projection just has to learn to occupy the shared space usefully. This is the same fusion pattern used again in Lesson 7 and generalized in Lesson 9.

Step 2 — causal decoding, shifted targets

The sequence of event vectors goes through MaskedSelfAttention (Lesson 1/2) — each event only sees itself and earlier events. That means position i's output was built entirely from events 0..i, so it's exactly the right vector to use for predicting event i+1.

position 0's output predicts event 1, position 1's predicts event 2, position 2's (the last one) predicts the actual next purchase — the one nobody has observed yet.

Step 3 — three heads, three tasks, one shared trunk

package/insurance_decoder_block.py — InsuranceDecoderBlock
self.policy_head = nn.Linear(d_model, num_policies)  # logits — classification
self.age_head    = nn.Linear(d_model, 1)             # scalar — regression
self.price_head  = nn.Linear(d_model, 1)             # scalar — regression

Classification and regression losses live on completely different scales — cross-entropy might sit around 1–3, MSE on unnormalized prices could be in the tens of thousands. Adding them together naively would let whichever loss has the biggest numbers dominate the gradient, regardless of which task actually needs more attention.

Learning how strictly to grade each task

Instead of hand-tuning fixed loss weights, UncertaintyWeightedLoss makes each task's weight a learned parameter — one that trades off automatically against how noisy/predictable that task turns out to be (this is the homoscedastic uncertainty weighting idea from Kendall et al., 2018).

train_insurance.py — UncertaintyWeightedLoss
self.log_vars = nn.Parameter(torch.zeros(len(task_names)))  # start all tasks equally strict

def forward(self, losses: dict):
    total = 0.0
    for i, name in enumerate(self.task_names):
        precision = torch.exp(-self.log_vars[i])   # 1/sigma^2 — how strictly this task is graded
        total    += precision * losses[name] + self.log_vars[i]
    return total

The + log_var term is the regularizer that stops the model from just setting every precision to zero to make the loss trivially small — pushing precision up costs something, so it only goes up if the task's loss is actually shrinking in a way worth grading harder.

💡 Tip

loss_weigher.parameters() gets added to the same optimizer as the model — the task weights are trained by the exact same backprop step, not tuned separately.

Normalizer — fit once, reuse everywhere

train_insurance.py
age_normalizer.fit(all_ages)      # mean/std computed once, on the full training set
...
age_norm = age_normalizer.transform(age)          # before feeding the model
...
next_age = age_normalizer.inverse_transform(age_pred[0, -1]).item()   # back to real years

The model only ever sees zero-mean, unit-variance numbers — this keeps age (tens) and price (hundreds) on comparable scales so neither dominates gradient updates. inverse_transform converts predictions back to real units for a human to read.

⚠ Inconsistency / best practice — refit vs reuse

The single most common way to silently break this pattern: calling .fit() again on new data (e.g. a validation or production batch) instead of reusing the training-set mean/std. Every number downstream — losses, predictions, the inverse-transformed output — becomes inconsistent with what the model was actually trained on. Normalizer is fit exactly once, in train(), on all_ages/all_prices from the full training set, and reused everywhere after.

Inference: reading the last position

train_insurance.py — predict()
policy_logits, age_pred, price_pred = model(policy, age_norm, price_norm)

next_policy_id = policy_logits[0, -1].argmax().item()   # last position = the actual forecast
next_age   = age_normalizer.inverse_transform(age_pred[0, -1]).item()
next_price = price_normalizer.inverse_transform(price_pred[0, -1]).item()

probs = policy_logits[0, -1].softmax(dim=-1)
top3_probs, top3_ids = probs.topk(3)   # confidence, not just the argmax

To add a new event to a customer's history, you don't retrain or reshape anything — just append to the three input lists and re-run predict(); the causal mask means every earlier position's output is unaffected by the new last event.

⚠ Inconsistency / best practice — mock data is intentionally easy

The two customer archetypes (A→C→A→C… young/cheap, B→D→B→D… older/expensive) are deterministic, noise-light patterns designed to make the model converge fast and the predictions look obviously correct. Real purchase histories won't have this clean a signal — treat the plumbing here (fusion, shift-by-one targets, multi-task loss, normalization, inference) as the reusable part, not the specific numbers this model produces.

Checklist

  • Fuse mixed feature types by projecting each to d_model and summing.
  • Causal decoder + shift-by-one targets = next-event prediction, for free, at every position simultaneously.
  • Multi-task losses on different scales need weighting — learned uncertainty weights beat hand-tuned constants.
  • Normalize once on train data, reuse everywhere, inverse-transform only at the very end for humans to read.
