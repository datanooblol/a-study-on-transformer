Validation & Deployment

This is the one lesson that's not documenting something already in the repo — it's naming a real gap across all three training scripts and giving you a concrete way to close it.

Core concept — applies to every project in this repo
Files this lesson is about
  • train_insurance.py, train_insurance_representation_for_claim.py, main.py — none currently split off a validation set
  • dev.ipynb — the only working torch.save/torch.load example
  • model.pt — a checkpoint already sitting in the repo root from a past dev.ipynb run
⚠ Inconsistency / best practice — the actual gap

All three training loops (train_insurance.py, train_insurance_representation_for_claim.py, main.py) train on the entire dataset and report training loss only. There is no held-out split anywhere in this repo. A falling training loss tells you the model is memorizing something — it does not tell you whether that something generalizes to a customer it hasn't seen. For mock, cleanly-patterned data (Lesson 6's callout) this rarely bites, but it's exactly the habit that causes real damage on real data.

Adding a validation split

The smallest change that fixes this: hold out a slice of the dataset before training starts, and evaluate on it — with gradients off — at the end of every epoch.

sketch — applies the same way to any of the three training scripts
from torch.utils.data import random_split

dataset = InsuranceDataset(n_customers=500, seq_len=5)
n_val   = int(0.15 * len(dataset))
train_set, val_set = random_split(dataset, [len(dataset) - n_val, n_val])

train_loader = DataLoader(train_set, batch_size=32, shuffle=True)
val_loader   = DataLoader(val_set,   batch_size=32, shuffle=False)  # no need to shuffle eval data
sketch — end of each epoch
model.eval()
val_loss, correct, total, abs_err = 0.0, 0, 0, 0.0
with torch.no_grad():

💡 Tip

model.eval() / model.train() matter here because of LayerNorm's running behavior and (in package/transformer.py) Dropout — both of these blocks behave differently at eval time, so forgetting to toggle the mode silently changes your validation numbers.

Checkpointing — the pattern that already exists, just not in the training scripts

dev.ipynb already has a working save/load round-trip. This is the pattern to lift into any script once you're happy with a model:

dev.ipynb
# --- Save (after training) ---
torch.save(model.state_dict(), "model.pt")

# --- Load (later, for inference) ---
loaded_model = ContrastiveTransformerEncoder(vocab_size=51).to(DEVICE)  # same args as training
loaded_model.load_state_dict(torch.load("model.pt", map_location=DEVICE))
loaded_model.eval()
⚠ Inconsistency / best practice — a checkpoint alone isn't enough to redeploy

The model.pt already sitting in this repo's root is exactly this artifact — weights from a past dev.ipynb run. But state_dict() only stores weights, not the hyperparameters needed to reconstruct the model (vocab_size, d_model, n_heads...), the vocabulary mapping (policy_to_id), or the Normalizer mean/std. Without those, loading model.pt elsewhere means guessing at the exact constructor arguments and normalization stats used at training time — get any of them wrong and the model loads without error but produces silently wrong output.

What "deploying" actually means for a model this size

Nothing exotic — no serving infra needed for a repo at this stage. Concretely:

  1. Persist a sidecar alongside the weights, not just model.pt:
sketch
import json

torch.save(model.state_dict(), "model.pt")
with open("model_meta.json", "w") as f:
    json.dump({
        "num_policies": 10, "d_model": 64, "n_heads": 4, "max_len": 50,
        "policy_to_id": policy_to_id,
        "age_normalizer":   {"mean": age_normalizer.mean,   "std": age_normalizer.std},
        "price_normalizer": {"mean": price_normalizer.mean, "std": price_normalizer.std},
    }, f)
  1. Wrap predict() so a caller only ever needs raw history in, a forecast out — it already takes plain Python lists and returns human-readable units, which is most of the way to an API function signature.
  2. Version the pair — treat model.pt + model_meta.json as one unit (e.g. same filename stem, or a timestamped folder); loading one without its matching other half is the single most common way small models silently misbehave after a "successful" deploy.

Checklist

  • Hold out a validation split before training starts — even a small one turns "loss went down" into an actual signal.
  • Track a human-readable metric (accuracy, MAE in real units), not just the raw loss value.
  • model.eval() before evaluating, model.train() before resuming training.
  • Never ship model.pt alone — save the constructor hyperparameters, vocab, and normalizer stats next to it.
