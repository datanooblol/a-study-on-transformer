Hard parameter sharing

This is the standard name for what's happening here: one shared trunk (the customer vector), several independent heads, all trained together with one combined loss. Every gradient update nudges the shared encoder to be useful for all four tasks simultaneously, not just one.

Why it helpsWhere it can hurt
Cheaper than training four separate encoders — one forward pass through the backbone serves all four heads.If tasks pull in genuinely conflicting directions (negative transfer), forcing one shared representation can make every task slightly worse than training it alone.
Acts as a regularizer — a representation that has to be useful for four related targets is less likely to overfit to noise specific to just one.Requires the tasks to actually be related. These four (claim amount, lapse probability, payment, risk score) all derive from the same underlying customer behavior, so sharing is a reasonable bet here.
💡 Tip

Look at how the mock data is generated in generate_customer() — claim_amount, lapse_prob, pay_amount, and risk_score are all functions of the same underlying hospital_count, late_count, age, income signals. That shared causal structure is exactly what makes hard parameter sharing a sound choice here, not just a convenient one.

A second implementation of uncertainty weighting

Lesson 6 already covered UncertaintyWeightedLoss — learn a per-task precision instead of hand-tuning fixed weights. This file reimplements the same idea, but not identically:

def forward(self, losses: list[torch.Tensor]) -> torch.Tensor:
    total = 0.0
    for i, loss in enumerate(losses):
        precision = torch.exp(-self.log_vars[i])
        total     = total + precision * loss + 0.5 * self.log_vars[i]
    return total
⚠ Inconsistency / best practice — two defensible, different formulas

This isn't a bug in either file — it's two different (correct, for what each is doing) approximations of Kendall et al.'s multi-task uncertainty weighting (2018). The precise negative-log-likelihood term differs by task's assumed noise distribution: for regression (Gaussian noise), the correct penalty is 0.5 * log(σ²) — what this file uses, and what you'd want for this file's four regression-only targets. For classification (categorical noise), the commonly-used approximation drops the ½ factor — closer to what Lesson 6's version does, which is mixing one classification task with two regression tasks and uses one formula for all three as a simplification. Neither file is "wrong" for its own use case, but copying either one verbatim into a project with a different task mix without checking this factor would quietly mis-calibrate the learned weights.

Training loop — six normalizers instead of three

Every regression target (and every continuous input) still gets its own independently-fit Normalizer — the same fit-once-reuse-everywhere discipline as Lesson 6 and Lesson 7, just scaled up to six instances instead of three.

The training loop also prints the four learned task weights every 5 epochs (torch.exp(-loss_weigher.log_vars)) — worth watching directly: if one task's weight converges much lower than the others, that's the model telling you that task is noisier or harder to predict from this input, not that something is broken. The reverse is also worth watching for — a weight climbing steadily is only good news if that task's validation metric is improving alongside it; see Lesson 13 for a real run where a weight nearly 7×'d while its validation performance never moved, which is the opposite of reassuring.

All four heads use plain mse here, which assumes over- and under-predicting each target costs the same. Lesson 12 covers what to do when that assumption doesn't hold for one of your targets — asymmetric loss shaping, and reparametrizing the output entirely when a direction is truly impossible rather than just costlier.

print(f"  predicted risk score   : {risk_normalizer.inverse_transform(pred_risk[0]).item():.2f}")

Same discipline as every other applied project in this repo: each output goes through its own inverse_transform before being printed, so the numbers a human reads are back in real units (currency, probability, score) instead of the normalized space the model actually operates in.

⚠ Inconsistency / best practice — still no validation split

Same gap as everywhere else in this repo (Lesson 8) — train() here reports training loss only. With four tasks sharing one backbone, a held-out split matters even more than in the single-task case: it's the only way to tell whether the shared representation is actually generalizing, or whether one dominant task (watch the printed weights) is quietly overfitting while dragging the others' apparent performance along with it.

Checklist

  • Hard parameter sharing = one shared trunk, several independent heads, trained jointly — cheap and regularizing when tasks are genuinely related.
  • Check the causal mix of your tasks (regression vs classification) before reusing an uncertainty-weighting formula wholesale from another project — the correct regularizer term depends on it.
  • Scaling to more targets means scaling the number of Normalizers, not changing the pattern.
  • Watch the learned task weights during training — they're diagnostic, not just a training detail.
