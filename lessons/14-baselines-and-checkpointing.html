Part 1 — a real theoretical baseline, not a guess

Lesson 13's callout was specific: compute the naive baseline from the known generating weights, not from raw label frequency. Here's why that distinction matters, and how to actually do it.

Working with real-world data, you never know the true process that generated your labels — the best you can do is estimate a baseline empirically (most-frequent-class accuracy, mean-prediction MAE) from the data you happen to have. Working with a mock dataset you wrote yourself, you have something almost nobody gets: the exact probabilities the generator used. That's not a consolation prize — it's a genuine advantage worth using. It lets you compute the actual Bayes-optimal accuracy: the best any model could possibly do, even with infinite data and a perfect fit, because the remaining error is pure randomness baked into the generator itself.

Working it out for next-item prediction

sample_category(age) assigns each category a weight that depends only on age. Given a specific age, the true probability of each category is that category's weight divided by the sum of all five weights — and the best any predictor can do, using only the age, is to always guess the single most likely category. sample_item_in_category() then picks uniformly among that category's 1-2 items, so the true item-level ceiling multiplies in that extra uncertainty too:

theoretical_baseline.py
def theoretical_item_ceiling(age: float) -> float:
    """Bayes-optimal probability of guessing the exact next item correctly,
    using the generator's own category weights — the best any model can do."""
    weights = {
        "Term":            max(0.1, 1.5 - age / 40),
        "CriticalIllness": max(0.1, 1.2 - age / 50),
        "WholeLife":       min(1.5, age / 35),
        "Endowment":       min(1.3, age / 45),
        "ILP":             0.7,
    }
    total = sum(weights.values())
    best_cat, best_cat_weight = max(weights.items(), key=lambda kv: kv[1])

    cat_prob            = best_cat_weight / total                    # P(best category | age)
    item_prob_given_cat = 1 / len(ITEM_IDS_BY_CAT[best_cat])          # uniform pick within that category
    return cat_prob * item_prob_given_cat


# average over the actual ages seen in validation — each val_expanded row is
# (items, ages, prices, sum_insures, next_item, next_age, next_price, next_sum_insure)
current_ages = [ages[-1] for (items, ages, prices, sum_insures, *_ ) in val_expanded]
ceiling = sum(theoretical_item_ceiling(age) for age in current_ages) / len(current_ages)

print(f"theoretical best possible next-item accuracy: {ceiling:.1%}")

Once this number exists, "the model gets 19-21% accuracy" stops being a vibe and becomes a comparison: close to the ceiling means the model is doing about as well as the data allows; well below it means there's real headroom and something about the model or training setup is leaving performance on the table.

⚠ Worth knowing — this exact trick doesn't survive contact with real data

This works because you wrote the generator and know its exact weights. With real customer data, nobody hands you the true underlying probability distribution — you'd fall back to the cruder empirical baseline (most-frequent-class accuracy, or a simple logistic regression as a "how hard is this really" sanity check) instead. Treat this exact technique as something specific to working with synthetic data, not a general recipe — the principle (compare against the best achievable, not against zero) is what generalizes, not this specific formula.

Part 2 — checkpoint tracking and early stopping

The fix for "epoch 50 was worse than epoch 15" is mechanical: save the model's weights whenever validation improves, and stop training once it's been flat for long enough that continuing is just buying overfitting.

checkpointing.py
best_val_loss = float("inf")
patience = 3                    # consecutive non-improving checks to tolerate
checks_without_improvement = 0
best_state_dict = None

for epoch in range(EPOCHS):
    model.train()
    # ... training loop exactly as before ...

    if (epoch + 1) % 5 == 0:
        model.eval()
        val_loss_total = 0.0
        # ... compute val_loss_total the same way total_loss is computed in training,
        #     using loss_weigher on the four validation losses ...
        model.train()

        current_val_loss = val_loss_total / len(next_item_val_loader)

        if current_val_loss < best_val_loss:
            best_val_loss = current_val_loss
            best_state_dict = {k: v.clone() for k, v in model.state_dict().items()}
            checks_without_improvement = 0
            print(f"epoch {epoch+1:3d} | new best checkpoint (val loss {best_val_loss:.4f})")
        else:
            checks_without_improvement += 1
            if checks_without_improvement >= patience:
                print(f"epoch {epoch+1:3d} | no improvement for {patience} checks — stopping early")
                break

model.load_state_dict(best_state_dict)   # restore the best version seen, not whatever's currently loaded

Illustrative shape — validation loss dips to a real minimum, then drifts back up as the model overfits. The checkpoint saved at the dip is the one worth keeping; everything in the shaded window afterward is patience running out before training actually stops.

💡 Tip — why .clone() matters

model.state_dict() returns references to the model's live parameter tensors, not a snapshot. If you save it without copying, best_state_dict keeps pointing at the same tensors the model continues training on — by the time you go to use it, it's silently identical to the current (possibly overfit) weights, not the good checkpoint you thought you saved. .clone() on every tensor is what actually freezes a copy in place.

One design choice worth naming: with four tasks and four different validation metrics, tracking the combined UncertaintyWeightedLoss value (the same number already being minimized in training) is the natural single number to select checkpoints on — it doesn't require arbitrarily deciding that one task (item accuracy? age MAE?) matters more than the others for the purpose of deciding "is this the best epoch."

Bringing both together

The two techniques answer two different questions, and both matter before trusting a result: checkpointing answers "is this actually the best version of this model I trained, or just whatever epoch I happened to stop at" — and the theoretical ceiling answers "given the best version, is there realistically more to gain, or is this close to as good as this task allows." Skipping either one risks the same mistake: judging a model by an arbitrary number (the last epoch, or zero) instead of the two numbers that actually mean something (the best it achieved, and the best it could have achieved).

Glossary

Bayes-optimal / theoretical ceiling
The best possible performance any model could achieve on a task, given the irreducible randomness in how the labels were actually generated — computable exactly when you know the true generating probabilities.
Checkpoint
A saved copy of a model's weights (state_dict) at a specific point in training, kept so you can return to it later instead of only ever having the current (possibly worse) weights.
Patience
The number of consecutive validation checks allowed to pass with no improvement before early stopping triggers.
Early stopping
Halting training once patience runs out, instead of running a fixed epoch count regardless of whether validation is still improving.
State dict
A Python dictionary mapping each parameter's name to its current tensor value — what model.state_dict() returns, and what needs to be .clone()'d to actually freeze a snapshot rather than a live reference.

Checklist

  • Compute a real baseline before judging a result — the generator's own known weights, when you have them, beat guessing.
  • Save a checkpoint whenever validation improves; restore it at the end, don't assume the final epoch is the best one.
  • Use patience to stop training once further epochs are clearly just overfitting, not progress.
  • .clone() every tensor in a saved state_dict — otherwise the "saved" copy silently tracks the live model instead of freezing a snapshot.
  • With multiple tasks, the combined loss is the natural single number to select checkpoints on.
