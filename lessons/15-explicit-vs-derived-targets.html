Explicit vs. Derived Targets

Where a target actually comes from decides three separate things downstream: how you construct X and y, how many times you normalize, and whether your loss function needs to mask anything. This lesson traces all three back to one root cause — and a third pattern (BERT's own trick) that shows it isn't really a binary choice.

Core concept — decides construction, preprocessing, and evaluation, any architecture

The question underneath the code

Every supervised training loop needs a target to compare its prediction against, and that target comes from exactly one of two places:

  1. Explicit — the target is its own stored value, independent of whatever the model reads as input.
  2. Derived — the target isn't stored anywhere on its own; it's produced by slicing or transforming a tensor you already have.

It's tempting to shortcut this to "decoders derive, encoders don't" — this repo's own examples make that look true at first glance. It isn't a rule. It's a coincidence of two genuinely independent questions lining up neatly in the cases we've built so far. Separating those two questions is the actual point of this lesson.

Two questions, not one

Before deciding how to build X and y, ask both of these — independently:

Same kind of data as the input, just a different position?A genuinely different quantity, never part of the input sequence?
Causal mask + per-position output preserved✅ Derivable — slice it out, no separate storage needed (Lesson 6, 9)moot — if it's a different quantity, there was never anything to slice, regardless of the mask
No causal mask, or output collapsed to one vector⚠️ Explicit anyway — same nature of target a decoder could derive for free, but this architecture can't get it safely or structurally (your multi-task encoder path)🚫 Explicit, and for a completely separate reason — Lesson 7's claim_amount fails on data type alone

Decoder-style shift-by-one satisfies both questions at once, which is exactly why it feels like "the" pattern. But the two failure modes in that table come from different places — one is about what the data is, the other is about what the architecture's structure allows — and conflating them is what makes "encoder = explicit" feel like a rule instead of a coincidence.

Why causality is the actual reason, not architecture labels

Here's the precise version of the second question. A decoder's output at position i was built using only positions 0..i — the causal mask (Lesson 1/2) guarantees it. So comparing position i's output against the true value at position i+1 is a fair test — the model could not have seen the answer. An encoder has no such guarantee: bidirectional attention means position i's output has already attended directly to position i+1. Attempting the same "shift and compare" trick there isn't a prediction task at all — the answer is already inside the representation you'd be reading it from.

Case 2a — explicit because the data type doesn't match (Lesson 7)

claim_amount was never part of the purchase/claim/payment sequences — it's an independently observed outcome, not "the next value" of anything in the input:

train_insurance_representation_for_claim.py — train()
claim_norm = claim_normalizer.transform(claim_amount)   # a SEPARATE tensor, its own normalizer
pred = model(purchases, claims, payments, profile_norm)
loss = loss_fn(pred, claim_norm)

No architecture, causal or not, could derive this by slicing — there's nothing in the input sequences that is a claim amount one step later. This fails the first question in the table, full stop.

Case 2b — explicit despite matching data type (your multi-task encoder path)

This is the case worth sitting with, because it's the one that breaks "encoder = explicit" as a clean rule. Predicting next item/age/price/sum_insure is the same kind of data as the input sequence — exactly like Lesson 6. The reason it still needs expand_into_prefixes building explicit rows isn't the data at all. It's that CLS pooling collapses the whole sequence into one vector before you ever get a prediction — there's no per-position dimension left to slice afterward — and there's no causal mask either, so even if the dimension survived, slicing it would leak exactly like the bidirectional diagram above. Two separate failures of the second question, at once.

Case 3 — hide the answer instead of avoiding the setup (BERT's MLM)

Lesson 11's Masked Language Modeling shows there's a third option, not just "give up and store the target separately." BERT keeps the bidirectional encoder and keeps the target conceptually inside the sequence — it solves the leak a different way: replace the specific input position being predicted with [MASK], so there's nothing left at that position for attention to leak.

What this means for preprocessing

DerivedExplicit
Normalization calls neededone per continuous feature — slice afterone per continuous feature, including the target
When slicing happensafter normalizing, inside the training loopN/A — nothing to slice

⚠ Inconsistency / best practice — where a real bug came from

A multi-task encoder project had a normalization helper built for exactly the explicit shape — three inputs, three separately-stored targets, six .transform() calls. When a decoder-style project needed the derived pattern instead — three inputs, no separate targets at all — that six-argument helper didn't fit. Writing the three calls out by hand, without a matching helper's structure to lean on, is exactly how two of them ended up calling the wrong normalizer (price and sum_insure both accidentally used age_normalizer) — a slip that ran with no error and silently trained on the wrong scale. A helper built for one shape will actively mislead you in the other.

What this means for evaluation

This is the part worth understanding as deeply as the normalization half, because it's the same root cause showing up somewhere completely different: whether your loss function needs to mask anything at all.

Explicit (prefix-enumeration)Derived (shift-by-one)
Can the target ever be padding?No — every row is constructed to have exactly one valid targetYes — slicing a padded sequence still contains PAD positions in the result
Classification lossplain cross_entropy, nothing to maskcross_entropy(..., ignore_index=0) — masking built in
Regression lossplain mse_loss, nothing to maska hand-written masked_mse — no built-in equivalent exists

Why the asymmetry between the two losses: CrossEntropyLoss ships with ignore_index because classification targets are discrete — PAD can be assigned its own reserved class id (0) and the loss can special-case it. Continuous regression targets have no equivalent "reserved value" to special case — a padded age is just a number like any other — so PyTorch has no generic way to know it's fake. You have to supply that knowledge yourself, which is exactly what masked_mse is for.

✓ Pattern worth reusing — the same masking idea, generalized

ignore_index-style masking isn't really "a padding feature" — it's a general tool for "some positions in my target tensor aren't valid to grade." Padding is one reason a position might be invalid (Lesson 6's decoder). BERT's MLM has the exact same requirement for a completely different reason: only the positions that were actually masked should contribute to the loss — every unmasked position must be ignored too, or the model would be graded on predicting words it was already shown outright. Same mechanism (mask out the invalid positions before averaging), two unrelated reasons to need it.

Putting all three together

Is the target the same kind of data as the input, just shifted?
↓ no → explicit, for a data-type reason (Lesson 7)
Does this architecture keep a causal mask AND a per-position output?
↓ no → explicit anyway, for a structural reason (your encoder path) — or hide the input instead (BERT)
Derivable — normalize once, slice after, mask the loss for padding

Three consequences fall out of wherever you land on this: how many things you construct as separate tensors, how many times you call .transform(), and whether your loss functions need ignore_index or a hand-written mask at all. All three trace back to the same one or two questions — they aren't three separate design decisions to make independently.

Glossary

Explicit target
A target stored as its own value, independent of the model's input tensors.
Derived target
A target produced by slicing or transforming a tensor you already have — no separate storage.
Attention leakage
When a position's output already had direct access to the value it's being asked to "predict," making the prediction meaningless — the failure mode a causal mask exists to prevent.
Hidden-then-predict
A third pattern (BERT's MLM): keep the target positionally inside the sequence, but remove the specific input at that position so bidirectional attention over the rest stays valid.
ignore_index / masked loss
A general mechanism for excluding invalid target positions from a loss's average — built into CrossEntropyLoss for discrete targets, requires a hand-written mask for continuous ones.

Checklist

  • Ask two separate questions, not one: is the target the same kind of data as the input, and does this architecture's mask + output shape allow deriving it safely?
  • A causal mask is what makes "slice out the next position" a valid, non-leaking training signal — not an arbitrary decoder convention.
  • When both questions say yes, normalize once and slice after; when either says no, the target needs its own storage and its own normalization call.
  • There's a third option beyond "derive" or "store separately" — hide the specific input instead, as BERT's MLM does, if you want a bidirectional model to predict something already inside its own sequence.
  • Whether your loss needs a mask traces back to the same root cause: explicit targets are never padding by construction; derived targets inherit whatever padding the original sequence had.
