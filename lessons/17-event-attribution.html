Event Attribution: Occlusion & Leave-One-Event-Out (LOEO)

Every lesson so far explains how the model computes something, in general. This one is different: the model is already trained, it just made one prediction for one customer — which of that customer's past events actually caused it? Occlusion answers this by re-running the model with one event blanked out at a time and watching what changes. Applied position-by-position across a whole sequence, this is called Leave-One-Event-Out (LOEO).

Applies to both encoder-only and decoder-only — this lesson runs it on both and compares

The question this lesson answers

A trained model looks at a customer's purchase/claim/payment history and predicts: next item = category 4, next age = 62, next price = 1,192, next sum insured = 130,153. Fine — but why? Which specific past events pushed it toward that answer, and which barely mattered? None of Lessons 1–16 answer this, because they're all about architecture and training — how the model is built, how it learns. This lesson is about post-hoc explainability: probing a model that's already finished training, one prediction at a time.

Occlusion, and LOEO as its systematic form

Occlusion is the general idea: blank out part of the input, re-run the model, see how much the output moves. Big change = that part mattered a lot; near-zero change = it barely mattered. Leave-One-Event-Out (LOEO) is just occlusion applied in a loop — one customer event removed at a time, cycling through every position in their history, producing one importance score per event.

Why "delete and shift" breaks — and the clean fix

The obvious way to "remove" event c is to delete it from the list and shift everything after it down one slot. Under RoPE, that's wrong: RoPE's rotation angle depends only on a token's absolute position (Lesson 16), so shifting d, e, f, g, h into new slots changes their rotation too. You'd be measuring two things at once — "what changed because event c's information is gone" and "what changed because five other events got new position encodings" — with no way to tell them apart.

This repo's masking convention (True = PAD, pad_mask_source = items, padding_idx=0 — see Lesson 4) already gives us the fix for free: set the occluded event's item id to 0 and pass that same tensor as the mask source. That simultaneously (a) embeds it to the zero vector reserved for PAD, and (b) makes masked_fill(mask, -inf) block every other position from attending to it as a key — with the sequence length and every other token's position completely unchanged.

Two positions you can't occlude this way — and why

Two edge cases surfaced directly from running this on real trained models — both are structural, not bugs.

  1. The read-out position itself. For the decoder, the prediction you're reading comes from the last real position's own row — occluding it corrupts the query doing the reading, not just a memory being read. (The encoder has no such restriction — CLS is a separate token, always distinct from every event position.)
  2. The causal decoder's very first position. Under a causal mask, position 0 is legal to attend to only itself — there's no earlier position to fall back on. Occlude position 0, and its own row's only legal key is now also masked. Every score in that row is -inf.

A slow walkthrough of edge case 2 — a 3-position toy example

The claim above is easy to state and easy to misread as "position 0 just contributes nothing, which is fine." It's worth walking through with real arithmetic why that's wrong — the failure isn't "no information," it's NaN, and NaN doesn't stay put.

who each query is causally allowed to look at, in a 3-event sequence
Query positionAllowed keys
0{0} — only itself
1{0, 1}
2{0, 1, 2}

Position 0 is the only query with just one legal option. Every other position always has an earlier fallback.

Step 1 — occlude position 0: its own row loses its only option. Marking position 0 as PAD blocks key 0 for every query. For query position 0 specifically, key 0 was also its only causally legal key — keys 1 and 2 were already blocked by the causal mask (they're in the future). So all three scores in position 0's row are forced to -inf:

✕
✕

query = position 0's score row over keys {0, 1, 2} — every entry is -inf.

Step 2 — softmax of an all--inf row is undefined, not zero. softmax computes e^score for each entry, then divides by their sum. e^(-inf) = 0 for all three, so the sum is 0, and every weight is 0/0. That has no defined value — it isn't "all keys get zero probability," it's arithmetically undefined. Floating point represents an undefined result as NaN. So position 0's attention weights become [NaN, NaN, NaN], not [0, 0, 0].

Step 3 — that NaN becomes position 0's real output. The layer computes position 0's output as NaN·V₀ + NaN·V₁ + NaN·V₂. Any arithmetic touching NaN produces NaN, so this is a vector of NaNs. It gets added back via the residual connection and passed through LayerNorm — still NaN. After this layer, position 0's entire hidden state is NaN, every dimension.

Step 4 — the next layer: position 1 assigns position 0 a clean, correct 0.0. Position 1's allowed keys are {0, 1}. Key 0 is still masked (the same pad mask is reused at every layer), key 1 is open. This time the row is [-inf, s] for some real score s — not all -inf, so softmax resolves cleanly:

0.0
1.0

query = position 1's attention weights over keys {0, 1} — a properly computed, finite 0.0 on key 0. Masking is doing exactly what it should here.

Step 5 — but 0.0 × NaN = NaN, not 0.0. Position 1's output is 0.0 · V₀ + 1.0 · V₁. V₀ comes from applying a linear layer to position 0's hidden state, which is entirely NaN (step 3) — so V₀ = NaN. In IEEE floating point, multiplying by exactly zero does not "clean" a NaN: NaN means "this value is unknown," and zero times an unknown value is still unknown. So 0.0 × NaN = NaN, and position 1's output becomes NaN + 1.0·V₁ = NaN too — even though position 1 never intended to use position 0 at all, and its attention weight proves it correctly assigned zero importance.

Step 6 — this repeats, layer after layer. Every later position's weighted sum also touches V₀ (always with weight 0.0, always still poisoned), so by the final layer, whichever position you actually read out is NaN too. This is exactly what showed up mid-session: occluding position 0 alone turned every column of the LOEO output into NaN, while occluding positions 1 through length-2 was completely fine — because only position 0 ever produces the fully-masked row that creates the NaN in the first place. Any other occluded position still leaves its query at least one open, earlier fallback key, so its row is never entirely -inf and no NaN is ever created to begin with.

⚠ Inconsistency / gotcha — NaN via 0 × NaN, not a bug in your code

In short: masking correctly assigns a poisoned key exactly 0.0 attention weight, but if that key's own value is already NaN (because it had no legal keys of its own to attend to), the 0.0 weight does not neutralize it — 0.0 × NaN = NaN — and the NaN rides along through every later layer and position regardless of how small its assigned weight is.

The fix is one line — restrict the occlusion range so it never touches either edge case:

valid occlusion positions
positions = range(length) if architecture == "encoder" else range(1, length - 1)

Implementation

Two pieces: a single-sequence prediction helper that knows where each architecture's "one real prediction" lives, and a loop that occludes every valid position and records the delta.

sequences_to_multiple_outcomes.ipynb (excerpt)
def predict_one(model, architecture, items_list, ages_list, prices_list, sum_insures_list):
    length = len(items_list)
    items_t = torch.tensor(pad(items_list, MAX_EVENTS), dtype=torch.long).unsqueeze(0)
    ages_t = torch.tensor(pad(ages_list, MAX_EVENTS, 0.0), dtype=torch.float).unsqueeze(0).unsqueeze(-1)
    prices_t = torch.tensor(pad(prices_list, MAX_EVENTS, 0.0), dtype=torch.float).unsqueeze(0).unsqueeze(-1)
    sum_insures_t = torch.tensor(pad(sum_insures_list, MAX_EVENTS, 0.0), dtype=torch.float).unsqueeze(0).unsqueeze(-1)

    ages_norm = age_normalizer.transform(ages_t)
    prices_norm = price_normalizer.transform(prices_t)
    sum_insures_norm = sum_insure_normalizer.transform(sum_insures_t)

    with torch.no_grad():
        item_logits, age_pred, price_pred, sum_insure_pred = model(
            [items_t], [ages_norm, prices_norm, sum_insures_norm], pad_mask_source=items_t
        )

    if architecture == "decoder":
        # read out at the last real position -- the only genuinely unobserved prediction
        item_logits = item_logits[:, length - 1]
        age_pred = age_pred[:, length - 1]
        price_pred = price_pred[:, length - 1]
        sum_insure_pred = sum_insure_pred[:, length - 1]

    item_probs = item_logits.softmax(dim=-1).squeeze(0)
    return {
        "item_probs": item_probs,
        "age": age_normalizer.inverse_transform(age_pred).item(),
        "price": price_normalizer.inverse_transform(price_pred).item(),
        "sum_insure": sum_insure_normalizer.inverse_transform(sum_insure_pred).item(),
    }

def loeo_for_customer(model, architecture, items_full, ages_full, prices_full, sum_insures_full, customer_idx):
    items_prefix, ages_prefix = items_full[:-1], ages_full[:-1]
    prices_prefix, sum_insures_prefix = prices_full[:-1], sum_insures_full[:-1]
    true_next_item = items_full[-1]
    length = len(items_prefix)

    baseline = predict_one(model, architecture, items_prefix, ages_prefix, prices_prefix, sum_insures_prefix)
    baseline_prob_true = baseline["item_probs"][true_next_item].item()

    positions = range(length) if architecture == "encoder" else range(1, length - 1)

    rows = []
    for i in positions:
        items_occluded = items_prefix.copy()
        items_occluded[i] = 0  # PAD id -- zero-embedding AND invisible-as-key, positions untouched
        occluded = predict_one(model, architecture, items_occluded, ages_prefix, prices_prefix, sum_insures_prefix)
        rows.append({
            "distance_from_end": (length - 1) - i,
            "item_prob_true_delta": baseline_prob_true - occluded["item_probs"][true_next_item].item(),
            "age_delta": baseline["age"] - occluded["age"],
            "price_delta": baseline["price"] - occluded["price"],
            "sum_insure_delta": baseline["sum_insure"] - occluded["sum_insure"],
        })
    return pd.DataFrame(rows)

Sign convention: impact = baseline − occluded. Positive means removing that event hurt the prediction (the event was helping); negative means removing it helped (the event was working against the eventual answer).

All five events are the same item id — a good stress test for redundancy. The earliest occurrence (position 1) has the largest positive item-probability delta, consistent with "the first occurrence establishes context; later repeats of the same item are increasingly redundant." Age barely moves at all (≤0.014 years) — not because history doesn't matter, but structurally: the decoder's age head computes age_pred = ages_norm + softplus(age_head(x)), where ages_norm at the read-out position is the customer's actual current age taken straight from the input, not from attention — only the small correction term depends on history at all. Price and sum_insure swing in both directions across adjacent same-item events (e.g. position 2: -1692, position 3: +851) — evidence the model tracks each event's actual noisy transaction amount, not just "item type present/absent."

Aggregating across 20 customers: the real finding

Running LOEO across 20 test customers and grouping by distance from the read-out position gives a much more reliable picture than any single example:

Architectureabs_item_mean rangeabs_price_mean rangeabs_sum_insure_mean range
Encoder (CLS-pooled)0.018 – 0.044196 – 4813,522 – 7,780
Decoder (causal, last position)0.0023 – 0.003227 – 45896 – 1,996

Every column, across every distance bucket (most with n=20 customers), the encoder's average |impact| is roughly 10× larger than the decoder's. That gap is structural, not incidental:

  • Encoder — single bottleneck. The whole prefix collapses through bidirectional attention into one CLS vector (Lesson 3). Every event is a co-equal contributor to that one vector, so removing any one of them measurably changes what it contains.
  • Decoder — distributed by training design. Shift-by-one supervises every position simultaneously (Lesson 16) — across many epochs the model had to produce a good "predict next" output starting from every possible prefix length, not just the one length we probe here. That pushes it toward encoding history redundantly across positions, so knocking any single one out barely moves the final read-out.

Equally notable: neither architecture shows a clean recency gradient. If "the most recent event matters most" were true, |impact| should shrink steadily as distance from the read-out grows. It doesn't — encoder's abs_item_mean bounces around with no monotonic trend across distances 0–6, and decoder's is close to flat across distances 1–5. Importance is spread roughly evenly across a history this short — a real finding about this mock dataset (item category depends mostly on the customer's current age band, which barely changes across a handful of consecutive events), not a failure of the method.

💡 Tip — don't compare raw magnitudes across features

abs_sum_insure_mean (thousands) will always dwarf abs_price_mean (hundreds) — that's just the underlying scale of the two quantities, not evidence that sum_insure is "more influenced." To compare relative sensitivity across features fairly, divide each by its own baseline predicted value (or its head's MAE) before comparing. Also watch sample size at the tail — buckets with fewer customers (the ones whose history reaches that far back) are noisier than the n=20 rows.

Where this fits among other attribution methods

Occlusion and LOEO sit inside a much wider family of post-hoc explainability techniques. The table below places them alongside the rest of the landscape — what each one actually does, what it needs access to, roughly how expensive it is, and where it tends to get used in practice:

Occlusion/LOEO was the right starting point for this repo specifically: it needs no extra library, reuses the existing masking convention exactly, and produces numbers ("removing this event changed the prediction by X") that are directly explainable to a non-technical stakeholder — a real advantage in a regulated domain like insurance. SHAP, LIME, and counterfactuals are the natural next step if this ever needed to satisfy formal model governance or regulatory review — they cost more to compute but carry stronger theoretical guarantees and, in SHAP's case, wider recognition from regulators.

Glossary

Post-hoc explainability
Explaining a specific prediction from an already-trained, frozen model — as opposed to anything about how the model is built or trained.
Occlusion
Blank out part of the input, re-run the model, measure how much the output changes. Large change = that part mattered; near-zero change = it didn't.
Leave-One-Event-Out (LOEO)
Occlusion applied systematically, one sequence position at a time, producing one importance score per event in a customer's history.
Mask-in-place occlusion
Occluding an event by marking it PAD (rather than deleting and reindexing) — removes its informational contribution while leaving every other token's position and rotary encoding untouched.
Degenerate attention row
A query position whose every legal key has been masked, producing an all--inf score row — softmax of that is NaN, and it propagates to other positions through 0 × NaN = NaN, not through any nonzero attention weight.
Bottleneck vs. distributed representation
A bottleneck (like CLS pooling) forces all information through one vector, making it sensitive to any single input changing. A distributed representation (like a decoder trained with per-position supervision at every prefix length) spreads redundant signal across positions, making any one position less individually load-bearing.

Checklist

  • Occlusion = remove part of the input and measure the prediction change; LOEO = occlusion looped over every event in a sequence.
  • Never delete-and-reindex under RoPE — it changes information content and position simultaneously. Mask-in-place (set the occluded event's id to the PAD id, reuse it as the mask source) changes only information content.
  • Two positions are structurally un-occludable this way: the read-out position itself, and — for causal decoders only — position 0, which has no attention fallback if masked (produces NaN that spreads via 0 × NaN, not a code bug).
  • Encoder's CLS bottleneck showed ~10× larger occlusion sensitivity than the decoder's distributed, every-position-supervised representation — a robust, architecture-level finding across 20 test customers.
  • Neither architecture showed a strong recency effect in this dataset — importance was roughly flat across position, itself a real finding worth noting rather than assuming recency always dominates.
  • Don't compare attribution magnitudes across features with different natural scales without normalizing first.
