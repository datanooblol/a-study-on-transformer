Linear Probing: How Much Information Is Actually There?

Lesson 17 asked which past events drove one specific prediction. This lesson asks a different question: forget any specific prediction — does the model's pooled representation contain enough information to recover a customer's next item, age, price, or sum insured at all, using nothing but a plain linear model trained on the frozen representation? If a deliberately weak reader can already decode something, that's strong evidence it's genuinely, simply present — not entangled somewhere only the original trained head can reach.

The question this lesson answers

A trained model has an item_head, an age_head, a price_head, and a sum_insure_head, each a small nn.Linear sitting on top of the shared backbone representation (Lesson 10). Those heads were trained end-to-end with the backbone, so their accuracy tells you what the whole system achieved together. It doesn't tell you whether the backbone's representation, on its own, already contained that information in an easily-readable form — or whether the head had to do serious nonlinear work to dig it out. Freezing the backbone and training a brand new, deliberately simple probe on top answers exactly that.

What "linear probing" means, and why weak is the point

Linear probing: take a trained, frozen backbone (no more gradient updates to it), run it on a batch of examples to get pooled representation vectors, then fit a plain linear model (logistic regression for a category, ridge regression for a number) on those frozen vectors against some attribute you care about. Nothing about the backbone changes — the probe is trained entirely separately, after the fact.

The choice to use a linear probe, specifically, is deliberate. A linear model is about the weakest possible reader you could use — it can only recover information that's already sitting in the representation in a simple, roughly-additive form. If even a linear probe decodes something well, that's evidence the information is genuinely, cleanly present — the result isn't an artifact of the probe being clever, because a linear probe isn't capable of being clever. If a linear probe fails, the information might still be in there, just tangled up in a way only a nonlinear reader (like the original trained head) can unpack.

Getting the representation before the heads touch it

model.backbone(...) is directly callable on both MultiTaskModel and MultiTaskDecoderModel — no need to hack apart forward(). For the encoder this returns the CLS-pooled summary vector directly, shape (batch, d_model). For the decoder it returns the full per-position output, shape (batch, seq_len, d_model) — so we index the same last-real-position read-out used everywhere since Lesson 16 and Lesson 17.

sequences_to_multiple_outcomes.ipynb (excerpt)
def extract_representation(model, architecture, items_list, ages_list, prices_list, sum_insures_list):
    length = len(items_list)
    items_t = torch.tensor(pad(items_list, MAX_EVENTS), dtype=torch.long).unsqueeze(0)
    ages_t = torch.tensor(pad(ages_list, MAX_EVENTS, 0.0), dtype=torch.float).unsqueeze(0).unsqueeze(-1)
    prices_t = torch.tensor(pad(prices_list, MAX_EVENTS, 0.0), dtype=torch.float).unsqueeze(0).unsqueeze(-1)
    sum_insures_t = torch.tensor(pad(sum_insures_list, MAX_EVENTS, 0.0), dtype=torch.float).unsqueeze(0).unsqueeze(-1)

    ages_norm = age_normalizer.transform(ages_t)
    prices_norm = price_normalizer.transform(prices_t)
    sum_insures_norm = sum_insure_normalizer.transform(sum_insures_t)

    with torch.no_grad():
        rep = model.backbone([items_t], [ages_norm, prices_norm, sum_insures_norm], pad_mask_source=items_t)

    if architecture == "decoder":
        rep = rep[:, length - 1]  # same read-out position as Lessons 16 and 17

    return rep.squeeze(0).numpy()
✓ Pattern worth reusing

Reusing model.backbone directly, instead of adding a flag to forward() or re-implementing the fusion+attention stack, keeps this probing code completely decoupled from the training code — it can't accidentally drift out of sync with how the model actually computes its representation.

Building a fair probe dataset

The probe reuses the exact same "prefix predicts the next event" framing the models were originally trained on — items_full[:-1] as input, items_full[-1] (and the matching age/price/sum_insure) as the target. That's what makes the probe's score directly comparable to the trained head's own score on the same task, rather than measuring something subtly different.

sequences_to_multiple_outcomes.ipynb (excerpt)
def build_probe_dataset(model, architecture, customers):
    X, y_item, y_age, y_price, y_sum_insure = [], [], [], [], []
    for customer_idx, items_full, ages_full, prices_full, sum_insures_full in customers:
        items_prefix, ages_prefix = items_full[:-1], ages_full[:-1]
        prices_prefix, sum_insures_prefix = prices_full[:-1], sum_insures_full[:-1]
        rep = extract_representation(model, architecture, items_prefix, ages_prefix, prices_prefix, sum_insures_prefix)
        X.append(rep)
        y_item.append(items_full[-1])
        y_age.append(ages_full[-1])
        y_price.append(prices_full[-1])
        y_sum_insure.append(sum_insures_full[-1])
    return np.array(X), np.array(y_item), np.array(y_age), np.array(y_price), np.array(y_sum_insure)
⚠ Inconsistency / best practice — the probe needs its own held-out split

None of this repo's train_insurance*.py scripts hold out a validation split for the model (Lesson 8's still-open gap). This side notebook already fixed that for model training (train_set/val_set/test_set). But the probe is a second, separately-trained model — it needs its own train/test split too, or its reported accuracy would just be memorization. sklearn.model_selection.train_test_split on the extracted representations handles this below.

sequences_to_multiple_outcomes.ipynb (excerpt)
from sklearn.linear_model import LogisticRegression, Ridge
from sklearn.model_selection import train_test_split
from sklearn.metrics import accuracy_score, r2_score

def run_linear_probes(model, architecture, customers, seed=55):
    X, y_item, y_age, y_price, y_sum_insure = build_probe_dataset(model, architecture, customers)
    (X_train, X_test, item_train, item_test, age_train, age_test,
     price_train, price_test, si_train, si_test) = train_test_split(
        X, y_item, y_age, y_price, y_sum_insure, test_size=0.3, random_state=seed
    )

    item_probe = LogisticRegression(max_iter=1000).fit(X_train, item_train)
    age_probe = Ridge().fit(X_train, age_train)
    price_probe = Ridge().fit(X_train, price_train)
    si_probe = Ridge().fit(X_train, si_train)

    return {
        "item_acc": accuracy_score(item_test, item_probe.predict(X_test)),
        "age_r2": r2_score(age_test, age_probe.predict(X_test)),
        "price_r2": r2_score(price_test, price_probe.predict(X_test)),
        "sum_insure_r2": r2_score(si_test, si_probe.predict(X_test)),
        "n_train": len(X_train), "n_test": len(X_test),
    }

Age is dramatically more linearly decodable than everything else — R² of 0.70–0.95, far above every other column. This is a genuine finding about the backbone itself, not a repeat of the age-head passthrough trick from Lesson 17 (age_pred = ages_norm + softplus(...) only happens later, inside MultiTaskModel.forward/MultiTaskDecoderModel.forward, strictly after backbone(...) returns — the probe never sees that passthrough input). The likely reason: age is smooth, roughly monotonic, and injected through a single linear projection per event with no per-transaction noise, so it dominates the pooled vector's variance and survives the fusion + attention pipeline almost perfectly intact.

Item accuracy sits right around chance level everywhere (0.087–0.174). With 8 real item categories, chance is ~12.5%. All 6 probes land close to that line — and so did the trained heads themselves on this same task (encoder/concat_all's own head hit 0.207, decoder/concat_all's hit 0.174, from the freshly-reloaded checkpoint metrics). That's a more useful finding than "which fusion strategy wins at item prediction": next-item prediction may be close to intrinsically hard for this mock dataset, not primarily an architecture or fusion-strategy shortfall.

Price R² is negative in 4 of 6 rows — the probe does worse than just predicting the mean price for every customer. Two things likely compound this: price carries real per-transaction lognormal noise on top of a category-based base amount (a genuine noise floor no probe can beat), and n_train=52 against a 32-dimensional input is a thin ratio for Ridge at default regularization — small-sample overfitting alone can push R² negative.

Sum_insure is weak-but-consistently-positive (0.04–0.32), a notch better than price in nearly every row — plausibly because sum insured correlates more with which item/policy type was purchased (something the representation clearly encodes, per Lesson 17's findings), whereas price carries more idiosyncratic per-transaction noise on top of that.

💡 Tip — what a negative R² actually means

R² (coefficient of determination) compares a model's predictions to the simplest possible baseline: always predicting the training mean. R² = 1 is a perfect fit, R² = 0 means "no better than guessing the mean," and R² < 0 means the fitted model is actively worse than that trivial baseline — a real signal that no reliable linear structure was recovered, not just "a weak positive correlation."

⚠ Inconsistency / best practice — don't over-read the fusion-strategy rankings

With n_test=23, precise differences between fusion strategies for the same feature (e.g. encoder concat_all price_r2 = 0.18 vs. encoder sum = -1.04) are well within what 23 samples can produce from noise alone — don't treat them as a real ranking. The cross-feature pattern (age ≫ sum_insure > item ≈ price, price often below the mean-baseline) is the trustworthy part of this table; the cross-fusion-strategy comparisons within one feature are not, at this sample size.

Probe vs. trained head — what the comparison actually tells you

If a frozen linear probe's score is close to the trained head's own score on the same task, the head isn't adding much beyond a simple linear read-out — most of the achievable signal was already sitting in the representation in an easily accessible form. If the probe scores much lower than the head, the head is doing real nonlinear work the probe structurally cannot reach.

A representation could, in principle, linearly encode something a trained head never learned to use (a wasted opportunity LOEO alone would never surface, since LOEO can only measure impact on predictions the model actually makes) — or vice versa, hold information only in a tangled nonlinear form no linear probe can reach, even though the trained head clearly benefits from it. Glossary

Linear probing
Freezing a trained model's representation and training a separate, simple linear classifier/regressor on top of it to test whether some attribute is easily, linearly recoverable — independent of whatever the model's own trained heads do with that representation.
Frozen representation
A representation extracted with torch.no_grad() from an already-trained model whose weights are not being updated further — the probe trains on top of it, never through it.
R² (coefficient of determination)
How much better a model's predictions are than always guessing the training mean. 1 = perfect, 0 = no better than the mean, negative = actively worse than the mean.
Chance-level baseline
The accuracy achievable with no information at all — for an 8-category classification task, roughly 1/8 = 12.5%. Scores near this line suggest the task may be intrinsically hard given the available signal, not just poorly modeled.

Checklist

  • Linear probing = freeze the backbone, train a brand-new simple linear model on its output, to test whether an attribute is cleanly, linearly present — independent of what the original trained heads do.
  • model.backbone(...) is directly callable, bypassing the prediction heads entirely — no need to modify forward().
  • The probe needs its own held-out split, separate from the model's own train/val/test split — otherwise its reported score is just memorization.
  • Age was dramatically more linearly decodable (R² 0.70–0.95) than item, price, or sum_insure — a real property of the backbone, not the age-head's separate passthrough trick.
  • Item accuracy sat near chance level for both the probes and the trained heads themselves — a hint that next-item prediction may be intrinsically hard in this dataset, not just under-modeled.
  • Negative R² means worse than predicting the mean — a real "no linear signal recovered" result, not a weak positive one.
  • With a small held-out set (n_test=23 here), trust the broad cross-feature pattern, not fine-grained rankings between fusion strategies.
