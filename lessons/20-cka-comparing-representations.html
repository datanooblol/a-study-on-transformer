CKA: Comparing Representations Across Models

Lessons 17–19 each looked at one trained model at a time — which events it used, how much it knows, what its representation looks like. This lesson asks a question those can't: across all 6 trained configs, which ones learned similar representations, and which learned genuinely different ones? Centered Kernel Alignment (CKA) answers that with one principled number per pair, instead of eyeballing six separate R² tables side by side.

The problem CKA solves: raw coordinates aren't comparable across models

Two independently trained models — even the same architecture, different random initialization — have no reason to agree on what any particular dimension of their representation "means." If a good representation gets rotated, reflected, or rescaled, every linear head trained on top of it still works exactly as well (it just learns different weights to compensate) — so gradient descent has no pressure to prefer one coordinate system over another. That means comparing two models' representations dimension-by-dimension is close to meaningless: "dimension 5" carries no consistent significance from one trained model to the next.

A concrete check: rotate three toy customers' 2D representation by 90°.

CustomerOriginal coordsRotated 90° coords
A(2, 1)(-1, 2)
B(5, 1)(-1, 5)
C(2, 4)(-4, 2)

Every single raw coordinate changed. But the pairwise distances didn't: A–B = 3 in both, A–C = 3 in both, B–C ≈ 4.24 in both. A naive per-dimension comparison would call these two representations unrelated. Anything that instead compares relative structure between examples — which is exactly what CKA does — correctly calls them identical.

What CKA actually computes

Instead of comparing raw vectors, CKA compares how similar every pair of examples is according to each representation, then checks whether those two similarity patterns line up. That's the piece that's invariant to rotation and scaling — relative distances between examples survive a rotation even though the raw coordinates don't, exactly as the toy example above showed.

The linear-kernel version used here has an efficient closed form, for two centered representation matrices X (n × d₁) and Y (n × d₂) over the same n examples:

linear CKA
CKA(X, Y) = ||Xᵀ Y||²_F  /  ( ||Xᵀ X||_F · ||Yᵀ Y||_F )

This is mathematically equivalent to the textbook definition (which compares n × n "how similar is example i to example j" Gram matrices for each representation), but computed via d × d products instead of n × n ones — more efficient whenever there are more examples than dimensions, exactly our case (≈75 test customers, 32-dim representations). Score range: 0 (unrelated structure) to 1 (identical structure up to rotation and scaling). The one hard requirement: both representations must come from the same set of examples, in the same order — X and Y can have different dimensionality, but not a different, unaligned set of rows.

Applying it to all 6 configs

Reuses Lesson 18's extraction pipeline exactly — CKA is a downstream analysis on representations already built for probing, not a new extraction step:

sequences_to_multiple_outcomes.ipynb (excerpt)
configs = [
    ("encoder", "sum"), ("encoder", "concat_all"), ("encoder", "concat_emb_summed"),
    ("decoder", "sum"), ("decoder", "concat_all"), ("decoder", "concat_emb_summed"),
]

models = {key: load_model(*key)[0] for key in configs}
probe_customers = collect_all_test_customers(min_len=2)

representations = {
    key: build_probe_dataset(model, key[0], probe_customers)[0]  # [0] = X, same customers for every config
    for key, model in models.items()
}

def linear_cka(X, Y):
    X = X - X.mean(axis=0, keepdims=True)
    Y = Y - Y.mean(axis=0, keepdims=True)
    hsic = np.linalg.norm(X.T @ Y, ord="fro") ** 2
    norm_x = np.linalg.norm(X.T @ X, ord="fro")
    norm_y = np.linalg.norm(Y.T @ Y, ord="fro")
    return hsic / (norm_x * norm_y)

cka_matrix = np.array([
    [linear_cka(representations[a], representations[b]) for b in configs]
    for a in configs
])

Architecture matters, but moderately, not dramatically. Average within-architecture similarity: encoder-to-encoder ≈0.73, decoder-to-decoder ≈0.79. Average cross-architecture similarity: ≈0.61. Same-architecture pairs are consistently higher — an independent, quantitative confirmation of Lesson 17's qualitative "these are different kinds of representations" claim. But nothing here drops near 0; all 6 configs still share substantial common structure, which makes sense since they're all solving the same task from the same fused input features, just wired differently.

Decoder configs form the tightest cluster in the whole matrix (0.76–0.82 among themselves) — tighter than the encoder configs are with each other (0.68–0.80). This lines up with a mechanistic story from Lesson 17: shift-by-one supervision at every position, across every prefix length seen in training, plausibly pushes the decoder toward a more redundant, distributed representation regardless of prediction task — and that same redundancy could make it less sensitive to which fusion strategy feeds it, producing more mutually consistent representations than the encoder's single-CLS-bottleneck manages.

Fusion strategy alone doesn't explain the pattern either. The single weakest link in the entire matrix is encoder/sum vs. decoder/sum (0.52) — the same fusion strategy across architectures is the worst match in the table, not a strong one. If fusion strategy dominated over architecture, same-fusion pairs should hold up reasonably well regardless of architecture; that's not what happened.

decoder/concat_all is the most "typical" representation of the six — highest average similarity to the rest of the group, including the strongest cross-architecture link anywhere in the table (0.72, to encoder/concat_emb_summed). encoder/sum is the most idiosyncratic — lowest average similarity to everything else, including that global-minimum link to decoder/sum.

💡 Tip — CKA tells you "how similar," not "which is better"

A high CKA score means two representations share structure; it says nothing about whether that shared structure is useful. Two very similar representations could both be equally mediocre, and two very different representations could both achieve strong downstream accuracy through genuinely different means. Pair CKA with something that measures task performance — Lesson 18's probe R²/accuracy is the natural partner here — before concluding a high-similarity pair is "the same, and good" rather than just "the same."

⚠ Inconsistency / best practice — linear CKA needs enough examples, and only sees linear structure

Two caveats worth carrying forward. First, CKA needs a reasonably sized, stable sample to mean much — with very few examples (like Lesson 19's 8-point item embedding table), CKA would be just as noisy as UMAP was there; this lesson's ≈75 test customers is a reasonable minimum, not a generous one. Second, the linear kernel used here — matching Lesson 18's "deliberately weak reader" philosophy for linear probes — only detects linear relationships between the two representations' structure. An RBF-kernel variant of CKA exists for nonlinear structure comparison; we didn't need it here, but it's the natural next tool if two representations score low on linear CKA yet still seem to behave similarly downstream.

None of these four replaces another — each answers a question the other three structurally can't. Occlusion never tells you what's in the representation overall; probing never tells you which specific event mattered; visualization never gives you a single comparable number across six models at once; CKA never tells you what a representation actually encodes, only how similar two of them are in structure.

Glossary

CKA (Centered Kernel Alignment)
A similarity measure between two representations of the same examples, invariant to rotation and isotropic scaling — compares the structure of pairwise example-similarity rather than raw coordinates.
Gram matrix
An n × n matrix where entry (i, j) is the similarity (e.g. dot product) between example i and example j under one representation — the "textbook" object CKA compares between two representations; the linear-kernel formula used here computes the same result more efficiently without ever forming it explicitly.
Rotation invariance
A property where rotating (or reflecting, or uniformly scaling) a representation doesn't change the measured similarity — necessary because independently trained models have no reason to agree on which raw direction means what, even if they encode the same information.
Linear vs. RBF-kernel CKA
Linear CKA detects only linear relationships between two representations' structure, mirroring the "deliberately weak reader" logic of Lesson 18's linear probes. RBF-kernel CKA can detect nonlinear structural relationships instead, at more compute cost.

Checklist

  • Raw coordinates aren't comparable across independently trained models — any rotation/reflection/scaling of a good representation is equally good, so gradient descent has no reason to align coordinate systems across runs.
  • CKA sidesteps this by comparing the structure of pairwise example-similarity instead of raw vectors — provably invariant to rotation and scaling.
  • Needs the same set of examples run through every representation being compared; dimensionality can differ, the example set cannot.
  • Our 6-config heatmap showed architecture matters moderately (within-arch ≈0.73–0.79 vs. cross-arch ≈0.61), decoder configs cluster tightest, and same-fusion-strategy pairs across architectures were not reliably similar (the global minimum was exactly such a pair).
  • CKA measures similarity, not quality — pair it with a task-performance metric (like Lesson 18's probe R²/accuracy) before concluding a high-similarity pair is "good," not just "similar."
  • LOEO, probing, UMAP, and CKA are complementary, not redundant — each answers a question the other three structurally cannot.
