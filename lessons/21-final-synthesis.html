Final Synthesis: Which Config Actually Wins?

Six trained configs (2 architectures × 3 fusion strategies). Four interrogation methods (Lessons 17–20), each giving a different partial answer. This lesson puts every number side by side and asks the question the whole side-project started with: which one should you actually use, and for what?

Scope: what's fully covered here, and what isn't

Worth being upfront about this before the table, rather than implying more rigor than what was actually done. Training metrics, linear probing, and CKA were all run across all 6 configs. LOEO (Lesson 17) was only run on 2 of 6 (encoder/concat_all and decoder/concat_all) — its finding (encoder ≈10× more occlusion-sensitive than decoder) is included below as an illustrative, plausible pattern, not a measured result for all 6. That was a deliberate scoping choice made to keep this a synthesis session rather than another full research session — see the checklist for what a full extension would take.

What the full table shows that no single earlier lesson did

Architecture cleanly wins on overall training performance — total separation. All 3 encoder configs (val_loss 3.38–3.52) beat all 3 decoder configs (3.87–3.97), with no overlap. Within each architecture, concat_emb_summed is the best fusion strategy — the same ranking holds in both groups. If you only read one number: encoder/concat_emb_summed is the best-trained config, full stop.

Age is where the story flips, and it's not visible at the head level at all. Every config's age_mae sits in a tight 1.26–1.31 band — the trained heads are nearly indistinguishable. But probe R² splits with zero overlap: decoder (0.91–0.95) entirely above encoder (0.77–0.82). Best explanation: the decoder's read-out is an actual sequence position — the customer's last real event — so that position's own current-age value rides straight through the residual connections into its own output, nearly for free (Lesson 16's causal-equivalence machinery guarantees this position's computation only ever depended on itself and earlier positions). The encoder's CLS token has no such privilege — it's a separate learned parameter that only ever receives age information secondhand, through attention. A read-out that is one of the input positions gets a structural advantage a dedicated pooling token doesn't.

Item and sum_insure show a genuine head-vs-representation divergence. decoder/concat_all has the single best trained item accuracy of all 6 (0.167) — yet one of the worst probe item accuracies (0.087). Its head is doing real nonlinear work a linear probe structurally can't reach. Sum_insure shows the same pattern in reverse: decoder heads get lower MAE than encoder heads (32.8–34.2k vs. 34.2–34.8k) despite encoder's representation being the only one with positive sum_insure R² (0.16–0.26, vs. decoder's near-zero-to-negative -0.03 to -0.59). Encoder's advantage on these two is "already linearly there"; decoder's is "extracted through nonlinear computation the probe can't see."

Price stays undecodable everywhere. Every single probe R² is negative — no config shows reliable linear price structure, encoder only "less bad" than decoder throughout.

CKA confirms decoder/concat_all as the most "typical" representation (highest avg CKA similarity, 0.733) and encoder/sum as the most idiosyncratic (0.624) — consistent with Lesson 20.

What this would mean for an actual deployment decision

If this were a real insurance business deciding what to ship, the honest read is: there's no single best config, and that's a real finding, not a non-answer. The right choice depends on what the model needs to be good at and how much it needs to explain itself:

  • Shipping one general-purpose model with the best aggregate performance → encoder/concat_emb_summed.
  • Building an age-driven risk or lapse model that also needs to survive a regulatory audit → decoder/concat_all, since its age signal is both the most accurate and the most linearly transparent — a friendlier substrate for the SHAP/LIME/counterfactual escalation path Lesson 17 already laid out, since those methods work better on cleaner structure.
  • Underwriting or sum-insured-focused pricing work → encoder/sum, the only config where that signal is genuinely, linearly present rather than buried in a nonlinear head.
  • An item-recommendation feature → none of the 6 are ready. Near-chance item accuracy across every config and every method (head and probe) is a real limitation of this mock dataset/setup, not something to paper over — it would need addressing (richer features, more data, a different task framing) before shipping.
⚠ Inconsistency / best practice — how much to trust this table

Two honesty checks before treating any of this as gospel. First, the probe numbers here were recomputed fresh in this session (a new random train/test split inside run_linear_probes each time) — small differences from Lessons 18/20's originally reported numbers are expected sampling noise, not a contradiction; with n_test≈23, don't over-read small gaps between configs. Second, this entire study used one mock dataset from one random seed — a real production decision would need this repeated across several dataset regenerations before trusting any single config's "win" as robust rather than a lucky draw.

Glossary

Capstone synthesis
Combining results from several independently-run analyses (here: training metrics, linear probing, CKA) into one comparison table — different from any single analysis, since patterns invisible within one method (like the age head-vs-probe split) only appear once multiple methods are placed side by side.
Head-vs-probe divergence
When a trained prediction head substantially outperforms a frozen linear probe on the same target, it means the head is doing real nonlinear extraction work — the information exists but isn't simply, linearly available in the representation itself.

Checklist

  • Encoder architecture wins cleanly on overall training performance (val_loss) across all 3 fusion strategies, with zero overlap against decoder.
  • concat_emb_summed was the best fusion strategy for both architectures.
  • Age showed a dramatic head-vs-representation split: near-identical MAE at the head level, but decoder's linear age R² (0.91–0.95) totally exceeds encoder's (0.77–0.82) — plausibly because the decoder's read-out is an actual input position, getting a "free" residual pass-through the encoder's separate CLS token doesn't.
  • Item and sum_insure showed the reverse pattern in places: decoder's trained heads beat encoder's on raw performance while encoder's frozen representation was more linearly informative — evidence decoder relies more on nonlinear extraction for these two.
  • No config solved item-level prediction — every config, by every method, sat near chance. A real, honest limitation of this dataset/setup.
  • There's no single "best" config — the right pick depends on which target and which interpretability requirement matters most for the deployment in question.
  • A full extension (LOEO + UMAP run across all 6, not just 1–2) would strengthen this further but wasn't done here — a deliberate scope decision, not an oversight.
