RoPE, End to End

Lesson 1 told you what RoPE does: rotate Q and K by an angle proportional to position. This lesson derives why that works, and traces every line of the real RoPE class — theta → angles → freqs → forward() — with concrete numbers at every step, so nothing is left as "trust the formula."

What this lesson adds beyond Lesson 1

Lesson 1 showed the rotation formula and asserted that dot products between rotated vectors end up depending on relative position. This lesson proves that algebraically and numerically, and walks the actual tensor shapes through RoPE.__init__ and RoPE.forward so you can trace every line against the real file with a concrete example in hand.

Step 1 — theta: one rotation speed per dimension pair

package/encoder_block.py — RoPE.__init__
theta = 1.0 / (10000 ** (torch.arange(0, dim, 2).float() / dim))

head_dim (called dim here) must be even — it's about to be split into pairs of dimensions, and each pair gets its own fixed rotation speed. torch.arange(0, dim, 2) gives the pair indices [0, 2, 4, ..., dim-2]; dividing by dim and raising 10000 to that power spreads the speeds across a wide geometric range — small pair-index → fast rotation, large pair-index → slow rotation.

Concretely, for dim = 8 (4 pairs):

worked example — dim = 8
pair index:      0        2        4        6
exponent:      0/8=0.00  2/8=0.25  4/8=0.50  6/8=0.75
10000^exp:        1        10       100      1000
theta:          1.0       0.1      0.01     0.001
rotation speed per dimension pair — bar height = theta (radians per position step)

Same idea as a clock's second/minute/hour hands: several rotation speeds running at once, fast ones for fine-grained distance, slow ones for coarse, long-range distance.

💡 Tip — why 10000?

It's the same base the original Transformer paper used for its sinusoidal positional encoding — an arbitrary but reasonable choice that spreads the slowest pair's wavelength out far enough to stay meaningfully distinct across long sequences, while the fastest pair still resolves adjacent positions. Nothing sacred about the exact number; it's a hyperparameter that happens to have become a convention.

Step 2 — angles: pairing positions with rotation speeds

package/encoder_block.py — RoPE.__init__
positions = torch.arange(max_len).float()
angles = torch.outer(positions, theta)   # (max_len, dim//2)

torch.outer(a, b) is every pairwise product: row i, column j of the result is a[i] * b[j]. Here that means: for every position, multiply it by every pair's rotation speed — how far that pair has rotated by the time you reach that position.

positionpair 0 (θ=1.0)pair 2 (θ=0.1)pair 4 (θ=0.01)pair 6 (θ=0.001)

Read a column top to bottom and you're watching one pair's angle accumulate at its own fixed speed as position increases. Read a row left to right and you're seeing every pair's current angle at one fixed position — the fast pair has already spun past 1 full radian by position 1, the slowest pair has barely moved.

Step 3 — freqs: storing cos/sin as a buffer

package/encoder_block.py — RoPE.__init__
self.register_buffer("freqs", torch.stack([angles.cos(), angles.sin()], dim=-1))
# shape: (max_len, dim//2, 2)

Every angle gets converted to its (cos, sin) pair up front — that's what the actual rotation formula needs, not the raw angle. Stacking on a new last axis of size 2 turns (max_len, dim//2) into (max_len, dim//2, 2): for every position and every dimension-pair, one cos and one sin, ready to use.

register_buffer (not nn.Parameter) is the correct choice here: freqs is fixed math with no gradient to learn, but it still needs to move to the right device with .to(device) and persist correctly in state_dict() — exactly the "tracked but not trainable" case that buffer exists for. And it's computed once at construction for the full max_len, not recomputed every forward call — forward() only ever slices into it.

Step 4 — forward(): applying the rotation, shape by shape

Concrete running example: batch=2, seq_len=4, n_heads=2, head_dim=8 (the same dim=8 from Step 1, so 4 pairs per head).

package/encoder_block.py — RoPE.forward
def forward(self, x: torch.Tensor) -> torch.Tensor:
    # x: (2, 4, 2, 8)  -- (batch, seq_len, n_heads, head_dim)
    seq_len = x.shape[1]                                  # 4

    freqs = self.freqs[:seq_len].unsqueeze(0).unsqueeze(2)
    # self.freqs[:seq_len]:            (4, 4, 2)        -- (seq_len, dim//2, 2)
    # .unsqueeze(0):                   (1, 4, 4, 2)      -- room for batch
    # .unsqueeze(2):                   (1, 4, 1, 4, 2)    -- room for n_heads

    x_pairs = x.unflatten(-1, (-1, 2))
    # (2, 4, 2, 8) -> (2, 4, 2, 4, 2)  -- head_dim=8 regrouped into 4 pairs of 2

    x0, x1 = x_pairs[..., 0], x_pairs[..., 1]   # each: (2, 4, 2, 4)
    cos, sin = freqs[..., 0], freqs[..., 1]     # each: (1, 4, 1, 4) -- broadcasts against x0/x1

    out0 = x0 * cos - x1 * sin                  # (2, 4, 2, 4)
    out1 = x0 * sin + x1 * cos                  # (2, 4, 2, 4)

    return torch.stack([out0, out1], dim=-1).flatten(-2)
    # stack:  (2, 4, 2, 4, 2)
    # flatten(-2): (2, 4, 2, 8)  -- back to x's original shape

Same shape in, same shape out — RoPE never changes head_dim, it only rotates values within it. The two unsqueeze calls on freqs exist purely so one shared set of angles can broadcast against every batch element and every head at once, with zero copying (Lesson 22's broadcasting rule, applied here).

Worked example — rotating one pair by hand

Take pair 0 (the fastest, θ = 1.0), at position 2, so the rotation angle is 2 × 1.0 = 2 radians. Start with a simple pair value (x0, x1) = (1.0, 0.0):

by hand
angle = 2.0
cos, sin = cos(2.0), sin(2.0)   # ≈ -0.416, 0.909

out0 = x0*cos - x1*sin = 1.0*(-0.416) - 0.0*0.909  = -0.416
out1 = x0*sin + x1*cos = 1.0*0.909  + 0.0*(-0.416) =  0.909
# (1.0, 0.0) -> (-0.416, 0.909)

The point rotates 2 radians (~114.6°) counter-clockwise around the origin — pure rotation, magnitude unchanged (still length 1). Verify it yourself: math.cos(2)**2 + math.sin(2)**2 == 1.

💡 Tip — try this in your notebook

import math; x0, x1 = 1.0, 0.0; angle = 2.0; c, s = math.cos(angle), math.sin(angle); out0, out1 = x0*c - x1*s, x0*s + x1*c; print(out0, out1) — should print the same -0.416..., 0.909... as above. This is the exact formula RoPE.forward runs, just for one pair by hand instead of every pair, every position, every head, at once.

Why rotation instead of addition — the algebraic payoff

Lesson 1 asserted that rotating Q and K makes their dot product depend only on relative position. Here's why, one pair at a time. Write the rotation of a 2D pair by angle a as a rotation matrix R(a). Rotating query q at position m and key k at position n by that pair's fixed speed θ gives:

algebra
q'_m = R(θ·m) q
k'_n = R(θ·n) k

q'_m · k'_n = q^T R(θ·m)^T R(θ·n) k

Two facts about rotation matrices finish the proof: they're orthogonal (R(a)^T = R(-a), rotating backward undoes rotating forward), and they compose additively (R(a) R(b) = R(a+b), two rotations in a row is one combined rotation). So:

algebra, continued
R(θ·m)^T R(θ·n) = R(-θ·m) R(θ·n) = R(θ·(n - m))

q'_m · k'_n = q^T R(θ·(n - m)) k

The absolute positions m and n are gone — only their difference n - m survives. Two tokens 3 apart contribute the identical rotation to their attention score whether they're at positions (2, 5) or (10, 13). This is the entire point of RoPE: relative position falls out of the dot product for free, with no distance number ever explicitly computed or fed to the model.

✓ Prove it yourself, numerically

Pick any 2D q, k, and θ. Rotate q by θ·2 and k by θ·5 (gap of 3), then separately rotate q by θ·10 and k by θ·13 (also a gap of 3). Both dot products come out identical — same proof style as Lesson 16's shift-by-one script, just for RoPE instead.

runnable in your notebook
import torch

def rotate(v, angle):
    c, s = torch.cos(angle), torch.sin(angle)
    x0, x1 = v[0], v[1]
    return torch.tensor([x0*c - x1*s, x0*s + x1*c])

q = torch.tensor([1.0, 0.5])
k = torch.tensor([0.3, 0.8])
theta = torch.tensor(0.3)

score_a = torch.dot(rotate(q, theta*2),  rotate(k, theta*5))    # gap = 3
score_b = torch.dot(rotate(q, theta*10), rotate(k, theta*13))   # gap = 3

print(score_a, score_b)   # equal (up to floating point)

Why several speeds together, not just one

A single rotation speed is periodic — it wraps around every 2π/θ positions, so two tokens far enough apart could rotate back to looking like they're close together for that one pair (aliasing, the same problem a clock's minute hand alone can't tell 5 past the hour from 65 past). Combining many speeds — fast pairs for fine local resolution, slow pairs that don't wrap within any realistic max_len — is what makes the full head_dim-wide rotation an effectively unique fingerprint of relative distance across the whole sequence, the same way second+minute+hour hands together uniquely identify a time that any single hand alone couldn't.

RoPE vs. other positional schemes

SchemeMechanismEncodesLearned?
Sinusoidal (original Transformer)Add a fixed sin/cos vector to the embedding, once, before any attentionAbsolute positionNo
Learned positional embeddingAn nn.Embedding(max_len, d_model) looked up by index, added to the token embeddingAbsolute positionYes
RoPERotate Q and K inside every attention layer, never touches the embedding or VRelative position (falls out of the dot product)No

The practical edge RoPE has: relative-position information is exactly what attention actually uses ("how far is this key from my query"), so RoPE delivers it directly instead of hoping the model learns to derive relative position by subtracting two absolute-position signals itself.

⚠ Inconsistency / best practice — five copies of this class

RoPE is copied verbatim into encoder_block.py, decoder_block.py, gpt_decoder_block.py, and insurance_decoder_block.py, plus a fifth, slightly different version in rope.py/transformer.py (used only by ContrastiveTransformerEncoder). Deliberate readability tradeoff for a study repo — every block file stays self-contained and diffable against the others — not an oversight. A production codebase would share one RoPE module instead.

💡 Tip — RoPE never touches V

Only Q and K get rotated. V carries the actual content being handed over once attention decides to look at a token — rotating it would scramble that content for no positional benefit, since V never participates in the position-sensitive dot product in the first place.

Glossary

theta (θ)
The fixed rotation speed assigned to one dimension-pair — radians of rotation per one step of position. Small pair-index → large θ (fast); large pair-index → small θ (slow).
angle
position × theta — how far a given dimension-pair has rotated by the time you reach a given position. Computed for every (position, pair) combination at once via torch.outer.
Rotation matrix, R(a)
The 2×2 matrix [[cos a, -sin a], [sin a, cos a]] that rotates a 2D point by angle a. Orthogonal (R(a)^T = R(-a)) and composes additively (R(a)R(b) = R(a+b)) — both facts are what make relative-position invariance fall out of the attention dot product.
Relative position invariance
The property that q'_m · k'_n depends only on n - m, not on m and n individually — the core payoff of rotating instead of adding.
register_buffer
PyTorch mechanism for state that must move with the module (.to(device)) and persist in state_dict(), but isn't a learnable parameter. freqs qualifies exactly: fixed math, computed once, reused every forward call.

Checklist

  • theta assigns one fixed rotation speed per dimension-pair, spread geometrically from fast (pair 0) to slow (last pair) via the 10000^(pair/dim) schedule.
  • angles = torch.outer(positions, theta) gives every (position, pair) combination's accumulated rotation in one call.
  • freqs stores cos/sin up front as a buffer — fixed, device-aware, persisted, computed once for the full max_len.
  • forward() never changes head_dim — unflatten groups it into pairs, rotates each pair, stack+flatten puts it back exactly as it was.
  • Rotating Q and K (never V) makes their dot product depend only on relative position — a direct consequence of rotation matrices being orthogonal and composing additively.
  • Multiple speeds together avoid the aliasing a single speed would suffer at longer distances — same idea as a multi-hand clock.
