Optimizers & Schedulers: Getting a Transformer to Converge

Every lesson before this one built the model. None of them asked how to actually get one to train well. This lesson is the layer between "I understand what a transformer is" and "I can reliably get one to converge" — AdamW's mechanics, why transformers specifically need warmup, cosine decay, and how to validate a learning rate for your own model instead of trusting a borrowed constant.

Core — applies to every architecture and every project in this repo

What this lesson covers, and what it doesn't

This spans four overlapping subtopics: optimizer theory (what Adam's beta1/beta2 actually track, why AdamW decouples weight decay), learning-rate scheduling (warmup + cosine decay, why transformers specifically need warmup), where hyperparameter defaults like 3e-4 or (0.9, 0.98) actually come from, and how to validate them for your own model rather than trusting convention. Data pipeline mechanics (Dataset/DataLoader/collate_fn) is real plumbing this all sits on top of, but it's already covered in Lesson 4 — not repeated here.

1. What Adam is actually tracking

Plain SGD updates a parameter by its raw gradient, scaled by one global learning rate — every parameter, every step, same treatment. Adam keeps two extra running estimates per parameter instead:

gradient g_tthis step's raw signal
→
m_t (1st moment)EMA of g_t — momentum, controlled by β1
→
v_t (2nd moment)EMA of g_t² — magnitude, controlled by β2

m_t answers "which direction has this parameter been consistently pushed?" — v_t answers "how large/noisy have this parameter's gradients typically been?"

Adam's update, per parameter, per step
m_t = β1 * m_{t-1} + (1 - β1) * g_t          # momentum
v_t = β2 * v_{t-1} + (1 - β2) * g_t**2        # magnitude tracker

m_hat = m_t / (1 - β1**t)                      # bias correction -- m_0=0, so early estimates are biased low
v_hat = v_t / (1 - β2**t)

param -= lr * m_hat / (sqrt(v_hat) + eps)      # the actual update

The payoff of v_t: dividing by sqrt(v_hat) makes the effective step size adaptive per parameter — a parameter with consistently large gradients gets its step shrunk (it's already moving fast, no need to push harder), a parameter with small/noisy gradients gets relatively more room to move. This is the entire reason Adam-family optimizers tend to need less manual per-parameter tuning than plain SGD.

💡 Tip — why bias correction exists

m_0 and v_0 both start at exactly 0, so early estimates are artificially pulled toward zero before enough steps have accumulated real signal. Dividing by (1 - β^t) — a factor that starts near 0 and rises toward 1 as t grows — inflates the early estimates back to their true scale. By the time t is large, β^t → 0 and the correction becomes a no-op.

2. AdamW — decoupling weight decay

Weight decay's goal is simple: shrink every weight a little each step, independent of the gradient, as a regularizer. Original Adam implements it by adding weight_decay * param directly into the gradient g_t before anything else happens — which means the decay term gets divided by sqrt(v_hat) too, exactly like the real gradient. A parameter with large, noisy gradients ends up decayed less than intended; a parameter with small gradients gets decayed more. The regularization strength ends up entangled with gradient statistics it was never supposed to depend on.

Adam (L2-via-gradient) vs. AdamW (decoupled)
# Adam: decay folded into the gradient, then divided by sqrt(v_hat) along with everything else
g_t = grad + weight_decay * param
... (m_t, v_t, bias correction as before, using this g_t)
param -= lr * m_hat / (sqrt(v_hat) + eps)

# AdamW: decay applied directly to the weights, completely separate from the adaptive update
... (m_t, v_t, bias correction using the REAL gradient only)
param -= lr * m_hat / (sqrt(v_hat) + eps)
param -= lr * weight_decay * param            # <- decoupled: same shrinkage for every parameter

That's the whole difference the "W" stands for. It's why torch.optim.AdamW, not torch.optim.Adam, is the default choice whenever weight decay matters at all — which for a transformer of any real size, it does.

3. Why transformers specifically need warmup

v_0 = 0, so v_hat in the first handful of steps is estimated from very little data — noisy, and often too small, which makes lr / sqrt(v_hat) spike far larger than intended right at the very start of training, before the estimate has had time to settle. Transformers are especially exposed to this: attention and the residual stream compound gradient scale across many stacked layers, and with random initialization, the first few steps can already be operating on a fragile, poorly-scaled loss surface. An oversized early update can knock the model into a bad region it never fully recovers from.

Warmup is the fix: start the learning rate at (near) zero and ramp it up linearly over the first few hundred/thousand steps, giving Adam's v_hat estimate time to stabilize before the learning rate reaches full strength. This isn't a theoretical nicety — the original "Attention is All You Need" paper's own optimizer schedule included it, and training transformers without it is a well-known way to watch loss diverge or plateau badly in the first few hundred steps.

4. Cosine decay, traced through your own code

After warmup, the learning rate doesn't stay flat — it decays smoothly toward a floor, following a cosine curve rather than a straight line or a sudden step down. Here's the actual function from learning_scheduler.ipynb:

notebooks/learning_scheduler.ipynb — get_cosine_schedule_with_warmup
def lr_lambda(current_step):
    if current_step < num_warmup_steps:
        return current_step / max(1, num_warmup_steps)          # linear ramp: 0 -> 1

    progress = (current_step - num_warmup_steps) / max(1, num_training_steps - num_warmup_steps)
    progress = min(progress, 1.0)
    cosine_decay = 0.5 * (1.0 + math.cos(math.pi * num_cycles * 2.0 * progress))
    return max(min_lr_ratio, cosine_decay)

Your own run used num_epochs=100, len(train_loader)=3 (5 samples, batch size 2 — ceil(5/2)=3 batches per epoch), giving num_training_steps=300 and num_warmup_steps=15 (5%). With num_cycles=0.5, the cosine term simplifies to 0.5 * (1 + cos(π · progress)) — a single smooth half-period, descending from 1.0 down to 0.0, never oscillating back up:

Linear ramp for 15 steps (5% of training), then a smooth cosine descent across the remaining 285 — steep in the middle, shallow near both ends, landing exactly at 0 on the last step.

Why cosine instead of linear decay: a straight line spends equal time at every learning rate. Cosine spends more time near the peak (giving the model longer at a productive learning rate before backing off) and more time near the floor (a longer, gentler fine-tuning tail at the end) — the steepest drop-off happens in the middle, where the model has already benefited from a while at high LR and can afford to move through the middle range quickly.

⚠ Gotcha — step the scheduler every batch, not every epoch

Your training loop calls scheduler.step() inside the inner batch loop, once per optimizer.step() — matching how num_training_steps was computed (num_epochs * len(train_loader), i.e. counting batches, not epochs). If you moved scheduler.step() outside to the epoch loop by mistake, the schedule would desync — the model would still be in "warmup" 3× longer than intended (100 epoch-steps instead of 300 batch-steps), and the whole curve would stretch out silently, with no error thrown.

5. Where the defaults actually come from

Every one of these numbers in your notebook is a convention someone found worked well, not a value derived from first principles for your specific model:

ValueWhere it comes from
lr = 3e-4Nicknamed the "Karpathy constant" — Andrej Karpathy tweeted it's "the best learning rate for Adam, hands down." A genuinely good empirical starting point for many small-to-medium models, not a theoretical result.
betas = (0.9, 0.98)GPT-family convention — a slightly lower β2 than Adam's original default (0.999) lets the second-moment estimate track recent gradient statistics a bit more responsively, found empirically to suit transformer training dynamics well when paired with warmup.
weight_decay = 0.1Also a GPT-style convention — noticeably higher than the more everyday default of 0.01, reflecting how much regularization large transformers tend to need.

All three are credible starting points, borrowed because they've worked for models broadly similar in shape to yours — not because they're provably optimal for your exact architecture, dataset, and batch size. Treat them as where you start tuning from, not where you stop.

6. Validating a learning rate for your own model — the LR range test

Not in your notebook yet, but this is the actual answer to "how do I know 3e-4 is right for my model": run a short warm-up training pass where the learning rate increases exponentially every step (not the schedule you'll actually train with — just a diagnostic probe), and plot the loss against the learning rate on a log scale.

sketch — not yet in your notebook
lrs, losses = [], []
lr = 1e-7
for X, y in probe_loader:                 # a handful of steps is enough, doesn't need to finish an epoch
    for g in optimizer.param_groups:
        g["lr"] = lr
    optimizer.zero_grad()
    loss = F.mse_loss(model(X), y)
    loss.backward()
    optimizer.step()
    lrs.append(lr)
    losses.append(loss.item())
    lr *= 1.3                              # exponential increase, e.g. ~1e-7 -> ~10 over a few hundred steps
    if loss.item() > 4 * min(losses): break   # stop once it's clearly diverging
what the resulting plot looks like — loss (y) vs. learning rate, log scale (x)

Loss stays flat while LR is too small to matter, drops fastest somewhere in the middle, then shoots up once LR is too large to be stable. A good peak LR is roughly one order of magnitude below where the divergence starts — comfortably inside the productive region, not right at its edge.

This is the concrete alternative to trusting 3e-4 blindly: run this once against your actual model and actual data (a few hundred steps is enough, no need to wait for a full epoch), read the LR off the plot where loss falls fastest, and use that as your schedule's peak — the same num_warmup_steps/ num_training_steps cosine shape from Section 4 still applies, just anchored to a peak LR you actually measured instead of borrowed.

The recipe to carry forward

  • Default to AdamW, not Adam, whenever weight decay matters — which for a transformer of any real size, it does.
  • (0.9, 0.999) is Adam's safe general default; (0.9, 0.98) is the transformer-specific convention, meant to pair with warmup.
  • Always warmup before training a transformer from scratch — typically 1–10% of total steps — regardless of which decay shape follows it.
  • Step the scheduler once per optimizer step (per batch), matching however num_training_steps was actually counted — check this explicitly, it's a silent desync otherwise.
  • Cosine decay down to a small floor (min_lr_ratio) rather than exactly 0 if you might continue training later — hitting exactly zero can make resuming awkward.
  • Treat borrowed constants (3e-4, (0.9,0.98), 0.1) as informed starting points, not answers — run an LR range test on your actual model before trusting one for a real training run.

Glossary

First moment (m_t)
An exponential moving average of the raw gradient, controlled by β1. This is what gives Adam its "momentum" — direction that's been consistent recently gets reinforced.
Second moment (v_t)
An exponential moving average of the squared gradient, controlled by β2. Tracks typical gradient magnitude per parameter, used to adaptively scale each parameter's effective step size.
Bias correction
Dividing m_t/v_t by (1 - β^t) to counteract both being initialized at zero — without it, early-step estimates would be artificially small.
Decoupled weight decay
AdamW's core change — weight decay is subtracted from parameters directly, never passed through the adaptive sqrt(v_hat) scaling the real gradient goes through.
Warmup
A linear ramp of the learning rate from (near) zero up to its target value over the first portion of training, giving v_hat time to become a reliable estimate before the LR reaches full strength.
Cosine annealing
A smooth, half-cosine-shaped decay of the learning rate from its peak down to a floor — shallow near both ends, steepest in the middle.
LR range test
A short diagnostic run where the learning rate increases exponentially every step while loss is logged, used to read off a good peak learning rate for a specific model and dataset instead of guessing.
