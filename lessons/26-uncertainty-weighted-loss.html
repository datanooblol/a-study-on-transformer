Uncertainty-Weighted Multi-Task Loss

Kendall, Gal & Cipolla, 2018 — the paper behind UncertaintyWeightedLoss in both train_insurance.py and train_insurance_representation_for_multi_tasks.py. This lesson derives it from scratch, proves the exact mechanism that makes it work with real calculus and real numbers, and connects every step back to the two implementations already living in this repo.

Core — applies to any multi-task head, in this repo or elsewhere
Files to have open alongside this lesson
  • train_insurance.py — dict-keyed UncertaintyWeightedLoss, 1 classification + 2 regression tasks
  • train_insurance_representation_for_multi_tasks.py — list-keyed version, 4 regression-only tasks
  • src/sequences_to_multiple_outcomes/loss_functions.py — the version used in this session's hand-built encoder, mixing both task types with the exact branch shown below
  • Lesson 10 — where this loss is first used, at the model level

The problem: whose loss gets to matter?

A multi-task model produces several losses per batch — say, an item-classification cross-entropy around 2.0, an age-regression MSE around 1.5, and a price-regression MSE that could be in the thousands if unnormalized. Add them together naively and the largest-scale task dominates every gradient step; the others barely get to influence the shared backbone at all. Hand-picking fixed weights to fix this is brittle — it has to be re-tuned every time a task's scale, difficulty, or dataset changes.

The core idea: let the model learn how much to trust each task

Treat each task's prediction as coming from a probability distribution with its own learnable variance σ² — a per-task "how noisy is this output, really" parameter, trained alongside everything else via ordinary backprop. Instead of hand-picking weights, take the negative log-likelihood of that distribution as the loss — the weighting falls out of the math automatically.

Deriving the regression term — the Gaussian case

Assume the model's prediction ŷ is the mean of a Gaussian, with task-specific variance σ²:

step by step
p(y | ŷ, σ²) = 1/√(2πσ²) · exp( -(y-ŷ)² / (2σ²) )

-log p(y | ŷ, σ²) = -log( 1/√(2πσ²) ) + (y-ŷ)² / (2σ²)
                   = ½ log(2πσ²) + (y-ŷ)² / (2σ²)
                   = ½ log(2π) + ½ log(σ²) + (y-ŷ)² / (2σ²)     <- constant term drops (no learnable params in it)

NLL  ∝  (1/(2σ²)) · (y-ŷ)²  +  ½ log(σ²)
     =  (1/(2σ²)) · L_mse   +  ½ log(σ²)

Two pieces, and both matter: a precision-scaled error term — divide the raw squared error by 2σ², so a task the model considers noisy (large σ²) gets its error term shrunk — and a regularizer, ½ log(σ²), that penalizes claiming unlimited confidence (σ²→0) without actually reducing the error. Without that second term, the model could trivially "cheat" by driving every σ² to zero and ignoring the error entirely.

The classification term — same shape, different distribution

For a classification head, Kendall et al. scale the softmax logits by 1/σ² (a temperature) and take the negative log-likelihood of that scaled softmax against the true class. The derivation involves an approximation of the softmax's normalizing constant that's less clean to reproduce exactly here, but the resulting shape is directly analogous to the regression case:

classification NLL, approximate form
L  ≈  (1/σ²) · L_crossentropy  +  log(σ)

Same two-part structure — precision-scaled error, plus a regularizer that grows as claimed confidence increases — just derived from a categorical likelihood instead of a Gaussian one, and without the clean factor-of-two that falls out of the Gaussian PDF's own exponent.

Why log_var, never σ² directly

Every implementation parameterizes log(σ²) as the actual nn.Parameter — not σ² itself:

src/sequences_to_multiple_outcomes/loss_functions.py
self.log_vars = nn.Parameter(torch.zeros(len(task_types)))
...
precision = torch.exp(-self.log_vars[i])   # = 1/σ², recovered from log_var

Two reasons: σ² must stay strictly positive, and an unconstrained parameter can't guarantee that — gradient descent could push a raw σ² parameter negative, which is nonsensical (variance can't be negative). Optimizing in log-space sidesteps the constraint entirely: log_var can be any real number, and exp(log_var) is guaranteed positive no matter what. It's also numerically friendlier — multiplying/dividing by σ² directly risks instability if it ever gets very small or very large; working in log-space keeps the numbers in a much better-behaved range.

The key mechanism — proving it with real calculus

This is the part that actually explains why a large-scale task doesn't drown out a small one. Fix a task's data-driven loss at some constant L (pretend, for a moment, that the backbone has stopped changing) and ask: what value of log_var would this task's own uncertainty parameter settle at, if it could freely minimize its own term?

solving for the optimal log_var, given a fixed L
f(v) = exp(-v)·L + v                        # v = log_var; using the classification-shaped term for clean numbers
f'(v) = -exp(-v)·L + 1 = 0
exp(-v) = 1/L
v* = log(L)                                  # the optimal log_var exactly matches log(the task's own error scale)

f(v*) = (1/L)·L + log(L) = 1 + log(L)        # <- the settled contribution to the total loss

Read that last line carefully: once a task's uncertainty has settled at its optimum, its contribution to the total loss is 1 + log(L) — logarithmic in its own raw error scale, not linear. A task with error 10,000 doesn't contribute 10,000 to the shared gradient signal — it contributes about 10.2. This is the entire mechanism, laid bare: uncertainty weighting doesn't just rescale losses by some fixed factor, it compresses the effective range of scales any task can dominate by.

That compression is exactly the effect that lets an unnormalized price-MSE task and a bounded cross-entropy task share one backbone without one silently starving the other of gradient signal.

the U-shape this is actually minimizing — total contribution vs. log_var, for a fixed L=10

Too negative (claiming high confidence): exp(-v)·L explodes faster than v can fall. Too positive (claiming total uncertainty): v grows without the precision term shrinking fast enough to compensate. The genuine minimum sits in between — that's what training actually converges toward.

Connecting it to the two implementations in this repo

Both are correct for the task mix they were written for — CLAUDE.md already flags this, and the derivation above explains exactly why the difference exists:

src/sequences_to_multiple_outcomes/loss_functions.py — the actual branch
precision = torch.exp(-self.log_vars[i])
if task_type == TaskType.CLASSIFICATION:
    total += (precision * loss) + self.log_vars[i]          # matches the classification derivation above exactly
else:
    total += (precision * loss) + (0.5 * self.log_vars[i])  # the extra ½ reflects the Gaussian NLL's own ½ log(σ²) term

train_insurance.py's dict-keyed version mixes 1 classification + 2 regression tasks and uses + log_var (no 0.5) as a simplification across all of them. train_insurance_representation_for_multi_tasks.py's list-keyed version is 4 regression tasks only, so it applies the Gaussian-specific 0.5 factor uniformly, matching every task's own derivation. Copying one file's version verbatim into the other's context would quietly apply the wrong constant to at least one task type — small in isolation, but it shifts each task's relative weight the moment several such terms are summed together, which is the entire point of this technique.

💡 Tip — reading precisions() after training

self.log_vars isn't just an internal detail — precisions() (exp(-log_var) per task) is a genuine diagnostic. A task with high precision (small σ²) is one the model considers reliably predictable; a task with low precision is one it's treating as inherently noisy. Reading this after training tells you something real about which of your targets the model actually trusts.

Glossary

Homoscedastic uncertainty
Uncertainty that's constant across all examples for a given task (one σ² per task), as opposed to heteroscedastic uncertainty, which would vary per example. This paper's whole mechanism is homoscedastic — log_vars has one entry per task, not per sample.
Precision
1/σ² — how tightly concentrated a distribution is. High precision = low variance = the model claims this task is predictable. Computed as exp(-log_var) throughout this repo's code.
Negative log-likelihood (NLL)
The loss used here — instead of hand-designing a loss function, assume a probability distribution over outputs and take -log of how likely the true value was under it. Minimizing NLL is equivalent to maximizing likelihood.
Settled contribution
What a task's loss term evaluates to once its own log_var has converged to its optimum for that task's current error scale — 1 + log(L) in the derivation above, growing logarithmically rather than linearly in the raw loss L.

Checklist

  • Multi-task losses summed with fixed weights let the largest-scale task dominate every shared gradient step — the actual problem this technique solves.
  • Each task's loss becomes a negative log-likelihood under an assumed distribution (Gaussian for regression, softmax for classification) with its own learnable variance.
  • Regression's precise term: (1/(2σ²))·L + ½log(σ²). Classification's: (1/σ²)·L + log(σ). Same two-part shape, different constant.
  • Parameterize log(σ²), never σ² directly — keeps variance positive with no explicit constraint, and stays numerically well-behaved.
  • The mechanism that actually matters: at its optimum, a task's settled loss contribution grows as O(log L), not O(L) — proven with real calculus above, not just asserted.
  • Don't copy the exact 0.5-factor convention between this repo's two implementations without checking the task mix — regression-only and mixed-task-type contexts use different constants for a real mathematical reason.
  • precisions() is a genuine post-training diagnostic, not just an internal detail — it reflects which tasks the model actually trusts.
