MLflow: From Training Script to Deployed Container

Getting a model from mlflow.start_run() to a running Docker container touched nine genuinely different systems — MLflow's serialization formats, its model registry, its two separate stores, a security feature, Docker networking, dependency locking, and Hydra's path resolution — each with its own failure mode. This lesson pulls the whole journey into one map, organized by concept instead of by the order the errors actually happened in, so the next project only needs the map, not the scars.

Core — every piece here is MLflow/Docker/uv mechanics, independent of model architecture
Files to have open alongside this lesson
  • scripts/mock_train_torch.py — logging, registration, and reproducibility artifacts
  • scripts/mock_inference_torch.py — loading a registered model by alias
  • scripts/fetch_artifacts.py — pulling the exact training-time manifest for a Docker build
  • Dockerfile — the full fetch → sync → run pipeline
  • config/config.yaml — tracking_uri, the single value that determines which architecture (below) you're actually running

Five stages, each independently correct-looking, each capable of silently breaking the next one — which is exactly what happened, repeatedly, until every stage agreed on the same underlying assumptions.

1. Logging a model — the serialization format choice

The basic instrumentation, inside with mlflow.start_run():

scripts/mock_train_torch.py
mlflow.log_params(OmegaConf.to_container(cfg.params, resolve=True))
mlflow.log_metrics({"train_loss": avg_train_loss, "val_loss": avg_val_loss}, step=epoch)
mlflow.pytorch.log_model(model, name="best_model", input_example=input_example, serialization_format="pickle")

Recent MLflow defaults mlflow.pytorch.log_model to serialization_format="pt2" — PyTorch's torch.export traced-graph format. That default demands two things a simple script won't have ready: an input_example tensor (to actually trace forward()), and a strict TensorSpec-shaped model signature. serialization_format="pickle" sidesteps both — it just pickles the live Python model object, no tracing required.

⚠ The tradeoff pickle makes

Pickling an nn.Module serializes the entire object graph — every submodule, every configured attribute, fully wired. Loading it back needs no manual reconstruction: no calling FusionEmbedding(...) or RoPE(...) yourself, the loaded object already has .backbone.fusion, .backbone.position_emb, everything, exactly as saved. The cost: pickle only stores a reference to each class (module path + class name), not its code — the exact class definitions must be importable wherever the model is loaded later.

2. The pickle-import gotcha

A class defined inside a script run directly (python mock_train_torch.py) gets pickled with its module recorded as __main__ — not the file's real name. A different script trying to unpickle it later needs that class accessible as __main__.ClassName too, which is not automatic.

scripts/mock_inference_torch.py
# Unused directly below, but required: pickle resolves classes by looking up
# `__main__.LinearLayer` at load time. Importing them here makes them attributes of
# *this* script's module -- which becomes `__main__` when run directly -- so unpickling
# finds them regardless of which file originally defined them.
from mock_train_torch import LinearLayer, SimpleNetwork, generate_dataset  # noqa: F401

This only bites __main__-run scripts. Classes living in a real installed package (this repo's own sequences_to_multiple_outcomes, declared under [tool.hatch.build.targets.wheel]) pickle with a stable package path instead — sequences_to_multiple_outcomes.embedding_layers.FusionEmbedding — and unpickle correctly via ordinary import resolution, no trick needed, as long as the package is installed wherever the model is loaded.

3. Registry versions and aliases — nothing moves by itself

Registering doesn't happen automatically just because a model was logged — it's a separate, explicit call:

scripts/mock_train_torch.py
# register exactly once per run, from the best checkpoint -- not inside the `if improved:`
# block, which would create a noisy new version on every single val_loss improvement
run_id = mlflow.active_run().info.run_id
mlflow.register_model(model_uri=f"runs:/{run_id}/best_model", name="mock-model")

Every training run that includes this line creates a new, independent version under mock-model — version 1, 2, 3, climbing forever. Loading by alias uses models:/mock-model@champion, but the champion alias only ever points at whatever version it was last explicitly assigned to:

reassigning champion — never automatic
from mlflow import MlflowClient
MlflowClient().set_registered_model_alias("mock-model", "champion", <new_version_number>)
⚠ The mistake this causes if missed

Retraining without reassigning the alias leaves champion pointing at an old version — a real, working model, just not the one you just produced. Every symptom looks identical to a genuine bug (missing files, stale code) because it genuinely is loading a different, older run than the one you're thinking about. Always check which run an alias actually resolves to before debugging further: MlflowClient().get_model_version_by_alias("mock-model", "champion").run_id.

4. The backend store vs. the artifact store — two separate systems

This is the one that cost three full debugging rounds, all producing the identical symptom (Failed to download artifacts from path 'pyproject.toml') from three different underlying causes. The starting confusion: MLflow tracks two categorically different kinds of data, in two independently configured places.

Backend storeArtifact store
What it holdsParams, metrics, tags, run status, registry metadataActual files — model weights, logged artifacts
Configured via--backend-store-uri--default-artifact-root or --artifacts-destination
This project's settingsqlite:///mlflow.db./mlartifacts

The artifact store has two fundamentally different access modes, and this is where everything actually went wrong:

local-path mode (--default-artifact-root) — client reads the filesystem directly
Cliente.g. fetch_artifacts.py
→
file:D:/.../mlruns/...a raw local path

Works only if the client can literally open that path — fine on the same host machine, impossible from inside a Docker container, which has its own isolated filesystem.

proxied mode (--artifacts-destination) — client goes through the server over HTTP
Cliente.g. fetch_artifacts.py
→
mlflow-artifacts:/...an HTTP request to the server
→
Serverreads the real file, streams it back

Works from anywhere that can reach the server over the network — including a Docker container — because the client never needs filesystem access to the artifact store at all.

⚠ The actual root cause, after two failed attempts at the flag alone

Switching the server to --artifacts-destination only changes the scheme for experiments created through the server. This project's training script had tracking_uri: 'sqlite:///mlflow.db' — a direct path to the database file, completely bypassing the running mlflow server process. Every training run created its experiment via direct file access, which falls back to a plain local file: artifact URI no matter what flag the (unused, for this purpose) server was given. The real fix was changing tracking_uri to http://127.0.0.1:5000 — routing training through the same server fetch/inference already used, so all experiment creation actually goes through the proxying logic.

✓ The transferable rule

Every component that touches MLflow — training, fetching, serving, a notebook, a teammate's laptop — must agree on the same tracking_uri, and it should be the server's HTTP address, not a direct path to whatever's backing it. Mixing "some things go through the server, some things access the file/DB directly" is what breaks proxying silently, with no error at the point the inconsistency is introduced — only later, wherever the mismatch actually gets exercised.

5. Server security — Host header validation

A different, unrelated error along the way: 403 Invalid Host header - possible DNS rebinding attack detected. This is a real MLflow security feature, not a bug — it validates the HTTP Host header against an allowlist, and host.docker.internal (Docker Desktop's DNS alias for reaching the host machine from inside a container) isn't on it by default.

the fix — configured on the server, not the client
mlflow server --backend-store-uri sqlite:///mlflow.db --artifacts-destination ./mlartifacts \
  --port 5000 --allowed-hosts "host.docker.internal:5000,localhost:5000,127.0.0.1:5000"
💡 Tip — this flag is backend-dependent

--allowed-hosts only works with MLflow's default FastAPI/uvicorn server. It silently doesn't apply if MLflow falls back to Flask/waitress (which happens on Windows without gunicorn available) — check mlflow server --help lists the flag at all before assuming it took effect.

6. Docker networking — reaching the host from inside a build

A server started with mlflow server --port 5000 in a normal terminal runs on the host machine. From inside a Docker build or container, localhost/127.0.0.1 refers to the container itself, not the host — a request there simply finds nothing listening. Docker Desktop provides a dedicated DNS name for this exact situation:

Dockerfile — passed as a build arg, resolved at build time
ARG MLFLOW_TRACKING_URI
ENV MLFLOW_TRACKING_URI=${MLFLOW_TRACKING_URI}
docker build --build-arg MLFLOW_TRACKING_URI=http://host.docker.internal:5000 -t mock-model-image .

This is also why the fetch step needs to run at build time in this Dockerfile — it needs live network access to the tracking server, which means the build environment (your machine, or CI) has to actually be able to reach it. A build environment with no network access to internal infrastructure would need this moved into an entrypoint script that fetches at container startup instead.

7. Reproducible environments — why pyproject.toml alone isn't enough

The actual motivation for all of this: MLflow's own auto-inferred requirements.txt doesn't know about a project's custom package or a custom package index (this repo's pytorch-cu130). The fix is to log the project's own exact dependency manifest as artifacts, and let uv rebuild the identical environment later:

scripts/mock_train_torch.py — logged once per run
repo_root = get_original_cwd()   # Hydra changes cwd to its own output folder -- a bare
                                   # relative path would look in the wrong place entirely
mlflow.log_artifact(os.path.join(repo_root, "pyproject.toml"))
mlflow.log_artifact(os.path.join(repo_root, "uv.lock"))
mlflow.log_artifact(os.path.abspath(__file__))   # this script itself -- LinearLayer/SimpleNetwork live here

pyproject.toml alone only has version ranges (torch>=2.11.0) — a fresh resolution against just that file, run later, isn't guaranteed to reproduce the exact versions that actually trained the model. Only uv.lock pins that exactly, which is why both get logged, and why the Docker build uses --frozen:

Dockerfile
RUN uv sync --frozen --no-install-project
FlagWhat it doesWhy it's here
--frozenRefuses to re-resolve; installs exactly what uv.lock saysFails loudly on drift instead of silently picking different versions than training used
--no-install-projectSkips building/installing the local project's own wheelThis mock example only needs mock_train_torch.py (fetched separately) — not the real sequences_to_multiple_outcomes package or README.md, neither of which is in this image
--no-sync (on uv run, at container start)Skips uv run's own implicit re-syncWithout it, every container start re-triggers the same local-project build attempt --no-install-project was used to avoid during the image build
⚠ The gotcha this last flag fixes

uv run <script> always double-checks the environment against the lockfile before running anything — a built-in convenience for local development, but a liability here: it doesn't inherit --no-install-project from the earlier explicit uv sync, so left alone it retries building the local package on every container start and fails the same way — missing README.md, missing src/. CMD ["uv", "run", "--no-sync", ...] tells it to trust the environment already built into the image, and skip re-verifying it.

8. The general artifact-logging model — planning your own structure

Sections 1 and 7 used log_artifact/log_artifacts for specific files. Here's the full mental model behind them, so a future project can be planned deliberately instead of copying calls one at a time.

Every run has an artifact tree — a filesystem-like hierarchy, rooted at that run's own artifact_uri. Every logging call adds something to that tree, at a location you control:

CallLogsBehavior
mlflow.log_artifact(local_path, artifact_path=None)One existing fileCopies that single file into the tree
mlflow.log_artifacts(local_dir, artifact_path=None)An entire local directoryRecursively copies everything inside it, preserving the directory's own internal structure

artifact_path is what decides where in the tree something lands. Leave it out and the item goes straight into the tree's root; provide a string and it's nested under that subfolder instead — this is the entire reason pyproject.toml/uv.lock/both scripts sit flat while config/ sits nested one level down:

scripts/mock_train_torch.py — same two calls, different placement
mlflow.log_artifact(os.path.join(repo_root, "pyproject.toml"))                      # no artifact_path -> tree root
mlflow.log_artifacts(os.path.join(repo_root, "config"), artifact_path="config")      # artifact_path="config" -> nested
the actual artifact tree this project's runs produce
<run's artifact_uri>/
├── pyproject.toml
├── uv.lock
├── mock_train_torch.py
├── mock_inference_torch.py
├── config/
│   └── config.yaml
├── best_model/          ← from log_model(..., name="best_model")
│   ├── MLmodel
│   └── data/model.pkl
└── final_model/         ← from log_model(..., name="final_model")
    ├── MLmodel
    └── data/model.pkl

log_model is really log_artifacts under the hood — it writes a small folder (weights + an MLmodel metadata file describing the flavor/signature) at the name= path, same tree, same rules.

Logging things that aren't already files

log_artifact needs something already sitting on disk. Most training-time objects aren't — a dict of results, a matplotlib figure, a pandas table. MLflow has purpose-built convenience loggers for the common cases, each one just a thin wrapper that serializes the object to a temp file and calls log_artifact for you:

ObjectCallLands as
A dictmlflow.log_dict(d, "results.json")A JSON (or YAML, by extension) file
A raw stringmlflow.log_text(s, "notes.txt")A plain text file
A matplotlib/plotly figuremlflow.log_figure(fig, "loss_curve.png")An image, viewable directly in the MLflow UI
Tabular data (list of dicts, dataframe)mlflow.log_table(data, "predictions.json")A JSON table with dedicated UI rendering (sortable/filterable)
✓ The universal escape hatch

No convenience method for your object type? Serialize it yourself — torch.save, np.save, json.dump, pickle.dump — to a local temp path, then log_artifact that path. Every convenience logger above is doing exactly this internally; there's nothing MLflow-specific about the serialization step, only about where the result ends up.

Reading it back — the mirror image

CallDoes
MlflowClient().list_artifacts(run_id, path=None)Browse the tree at one level — like ls. Returns objects with .path, .is_dir, .file_size
MlflowClient().download_artifacts(run_id, path, dst_path)Pull a file or a whole directory down to local disk (used throughout this lesson's fetch_artifacts.py)
mlflow.artifacts.load_dict(uri) / load_text(uri)Read straight into memory — no download-to-disk step — mirroring log_dict/log_text

9. Hydra's config_path — relative to the file, not the working directory

The last failure, after everything else finally worked: Primary config directory not found. Check that the config directory '/config' exists.

scripts/mock_inference_torch.py
@hydra.main(version_base=None, config_path="../config", config_name="config")

config_path resolves relative to the script's own file location, not the current working directory. Locally, the script lives at scripts/mock_inference_torch.py, so ../config correctly reaches the repo-root config/. The Dockerfile had originally copied the script flat into /app/mock_inference_torch.py — from there, ../config resolves to /config (the container's root), not /app/config where config/ actually landed.

Dockerfile — the fix: mirror the local directory layout, don't flatten it
# scripts/ one level below repo root, sibling to config/ -- exactly like the local repo,
# so ../config resolves the same way, and mock_train_torch.py sits next to the script
# that imports it (Section 2's pickle requirement)
RUN mkdir -p scripts && mv mock_train_torch.py scripts/
COPY scripts/mock_inference_torch.py ./scripts/
COPY config ./config

CMD ["uv", "run", "--no-sync", "scripts/mock_inference_torch.py"]
✓ The transferable rule

Any relative path baked into code — a Hydra config_path, a relative import, a relative artifact path — implicitly assumes a specific directory shape around it, not just the presence of the right files. A Dockerfile (or any deployment step) that copies files in flat, changing that shape, will break every one of those assumptions even though every individual file is present and correct.

Glossary

Backend store
Where MLflow keeps params, metrics, tags, and registry metadata — a database (SQLite, Postgres, etc.), configured via --backend-store-uri.
Artifact store
Where MLflow keeps actual files — model weights, logged artifacts. A completely separate system from the backend store, configured via --default-artifact-root (local-path mode) or --artifacts-destination (proxied mode).
Proxied artifact access
Clients fetch/upload artifact bytes via HTTP requests to the tracking server, which reads/writes the real storage on the client's behalf — the server acts as a proxy, so clients never need direct filesystem (or cloud-credential) access to the underlying store.
Registered model alias
A named pointer (e.g. champion) to one specific version of a registered model. Never moves automatically — reassigning it to a new version is always an explicit, separate step from registering that version.
Artifact tree
The filesystem-like hierarchy of files/directories logged to one run, rooted at that run's artifact_uri. artifact_path on any logging call chooses where in this tree the item lands — omitted, it goes to the root.
Convenience logger
A thin MLflow wrapper (log_dict, log_text, log_figure, log_table) that serializes a common in-memory object type to a temp file and calls log_artifact for you. For anything without a dedicated wrapper, serializing it yourself first and calling log_artifact directly always works.
--frozen (uv)
Installs exactly what a lockfile specifies, refusing to silently re-resolve anything — fails loudly if the lockfile and manifest disagree, rather than quietly picking different versions.

Checklist

  • Choose serialization_format="pickle" for simplicity (whole object graph, no tracing) or "pt2" for a portable traced format (needs input_example + a TensorSpec-compatible signature) — know which one you're getting by default in your MLflow version.
  • Pickled classes need to be importable wherever they're loaded — trivial for a real installed package, requires the __main__-import trick for a bare script.
  • Registering a model and assigning/moving an alias are two separate, always-manual steps — never assume an alias tracks "whatever I just trained."
  • Backend store (metadata) and artifact store (files) are configured independently — know which access mode (local-path vs. proxied) your artifact store is actually using before debugging a download failure.
  • Every component must share the same tracking_uri, pointed at the server's HTTP address — not a direct path to whatever backs it — or proxying silently doesn't apply to whatever bypassed the server.
  • localhost inside a container isn't the host machine — use host.docker.internal (or equivalent) to reach services running on the host.
  • Log uv.lock, not just pyproject.toml, if reproducibility matters — ranges aren't pins.
  • --no-install-project at build time and --no-sync at run time are a matched pair — needed together whenever the deployed image doesn't contain the full local project source.
  • log_artifact logs one file; log_artifacts logs a whole directory recursively — artifact_path on either one chooses where in the run's artifact tree it lands, root by default.
  • For anything that isn't already a file — a dict, a figure, a table — reach for the matching convenience logger (log_dict/log_figure/log_table) before hand-rolling a temp-file dance; for anything without one, serializing it yourself and calling log_artifact always works as the universal fallback.
  • Relative paths (Hydra config_path, relative imports) assume a directory shape, not just file presence — mirror the local layout in the deployment image rather than flattening it.
